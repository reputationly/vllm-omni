## 1. ⚠️ 最容易漏的一条：Category 必须手动填

`gpustack/scheduler/scheduler.py:724` 的 `_VLLM_OMNI_CATEGORY_HINTS` **目前只有一条规则**：

```python
_VLLM_OMNI_CATEGORY_HINTS = [
    ("minimax-h3", CategoryEnum.VIDEO),
    ("minimax_h3", CategoryEnum.VIDEO),
]
_VLLM_OMNI_DEFAULT_CATEGORY = CategoryEnum.TEXT_TO_SPEECH
```

也就是说 **除 MiniMax-H3 外的所有 vLLM-Omni 模型都会被默认归类成 `text_to_speech`**。
本次六个模型里有 **5 个会被归错**（Ideogram-4 / SenseNova-U1.5 / Krea2 归 image，LTX-2.5 归 video，
Music3 归 music），只有 IndexTTS-2.5 的默认值恰好是对的。

归错的后果不是报错，而是**静默不可用**：`is_image_model()` / `is_video_model()` / `is_music_model()`
（`schemas/models.py:859/868/877`）都读 `categories`，归错的模型在对应端点的模型列表里根本不出现。

**两条修法，二选一：**

- **运营侧（本次上线采用）**：建实例时在 UI 手动填 Category。
  `set_model_categories()` 在 `model.categories` 已填时早返回，**显式声明永远压过 hints**，安全。
- **代码侧（建议后续补）**：给 `_VLLM_OMNI_CATEGORY_HINTS` 补 5 条 token。注意源码注释里的告诫
  ——"宁可欠匹配不可过匹配，不要在语音 checkpoint 也可能带的 token 上加规则"。
  建议 token：`ideogram`→image、`krea`→image、`sensenova`→image、`ltx`→video、`music3`→music。
  其中 `ltx` 要留神：`ltx2-v2a`（视频配音）也含这个 token，但它同样是 video，不冲突。

## 2. GPUStack 建实例

权重路径：**计算节点视角**填 `/nfs-data/models/<目录>`（管理节点上是
`/nfs-models/wuhanjisuan894/models/<目录>`，两者是同一个 NFS share 的不同挂载点，GPUStack 填前者）。

### 2.1 三个图像模型

| | Ideogram-4 | SenseNova-U1.5 | Krea2 |
| --- | --- | --- | --- |
| 权重目录 | `Ideogram-4-NF4` | `SenseNova-U1.5-8B-MoT` | `Krea-2-Turbo` |
| Backend | vLLMOmni | vLLMOmni | vLLMOmni |
| gpus_per_replica | 2 | **2** | 1 |
| Category | `image` | `image` | `image` |
| Backend Parameters | `--quantization bitsandbytes --tensor-parallel-size 2` | `--num-gpus 2 --tensor-parallel-size 2` | `--quantization int8` |
| 生产分辨率上限 | 1024×1024（2048 未做 varlen 改造，见下） | 4K 可跑（TP=2 时） | 1024×1024（Int8 下 1536 已验证安全） |

三个各自的坑：

- **Ideogram-4 必须带 `--quantization bitsandbytes`**。不带的话 NF4 checkpoint 会被逐个反量化成 BF16
  常驻显存，双 DiT 18.6B×2字节 ≈ 37.2 GB + 8B 文本编码器，**必然撑爆 40G 卡**。带上之后
  权重 12.8 GB / 生成峰值 24.6 GB。这是设计层面的问题，不是调参能绕的。
- **Ideogram-4 的 2048² 不要开放**。`_build_segment_mask` 仍是稠密布尔 mask，2048² 下是
  16384×16384 的张量，没做 varlen 化。冒烟只验过 1024²。
- **Ideogram-4 的提示词必须是官方结构化 schema，这是硬阻塞项**。2026-08-28 服务态对照实验，
  同一个「灯塔/悬崖/夕阳」这种最无害的提示词：

  | 提示词格式 | 结果 |
  | --- | --- |
  | 简化 JSON `{"subject","style","scene","palette"}` | **两次全部被拦**，返回灰底 "Image blocked by safety filter" |
  | 官方 schema `high_level_description` + `style_description` + `compositional_deconstruction.background/elements[]`（每个 element 带 `bbox`/`desc`/`palette`） | **正常出图**，且 `bbox` 精确生效（指定的构图位置被严格遵守） |

  也就是说**不做转换层的话，正常业务提示词会被大面积误拦**。门面层必须实现
  "自由文本 → 官方结构化 schema" 的转换（见 Ideogram-4 报告 §5.6），
  并保留 "Image blocked by safety filter" 文案检测作为兜底。
- **Krea2 不支持图生图**（`pipeline_krea2.py` 的 `forward()` 签名里没有图像入参）。
  体验区不要给它挂 image2image tab。
- **Krea2 的 TP 是假的**：`ReplicatedLinear` 架构，每张卡存全量权重、算同样的东西，加卡只增开销。
  必须 1 卡。

### 2.2 LTX-2.5（四个开关一个都不能少）

权重目录 `Lightricks/LTX-2.5-Diffusers`，Category `video`。

```text
--model-class-name LTX2DistilledOneStagePipeline   # 5/10/15 秒档
--quantization int8
--enable-cpu-offload
--no-diffusion-compile-dynamic
--ulysses-degree <N> --vae-patch-parallel-size <N>  # N = 卡数
```

1080p 档改 `--model-class-name LTX2DistilledTwoStagePipeline`，N=4。

为什么一个都不能少（每条都有实测支撑，详见 LTX-2.5 报告 §2）：

| 开关 | 去掉会怎样 |
| --- | --- |
| `--quantization int8` | bf16 DiT 38 GB 单卡装不下 |
| `--enable-cpu-offload` | 24 GB 文本编码器与 DiT 同时常驻，OOM |
| **不能加 `--use-hsdp`** | HSDP 路径会无条件把 encoders 搬上卡，把 CPU offload 的托管放置盖掉，加载完即 38.5 GB |
| **不能用 `--enable-layerwise-offload`** | DiT 常驻主机内存每 rank 一份，4×38 = 152 GB，被 OOM killer 杀 |
| `--no-diffusion-compile-dynamic` | 慢 1.58~1.90×（44.3 s → 84.2 s） |

**分档与卡数**（实测，见 LTX-2.5 报告 §5）：

| 档位 | 尺寸 | 时长 | 卡数 | 耗时 | 峰值显存/卡 |
| --- | --- | --- | ---: | --- | --- |
| 标准 5 秒 | 960×544（+竖屏 544×960） | 5.04 s | **1** | 44.3 s | 27.9 GB |
| 标准 10 秒 | 960×544 | 10.4 s | **1** | 62.4 s | 35.2 GB |
| 标准 15 秒 | 960×544 | 15.04 s | **4** | 75.5 s | 33.5 GB |
| 高清 5 秒 | 1920×1088 两阶段 | 5.04 s | 4 | 100.0 s | 31.3 GB |
| 高清 10 秒 | 1920×1088 两阶段 | 10.4 s | 4 | 143.3 s | 37.2 GB |

- 15 秒档**必须 4 卡**：单卡 39.7 GB 只剩 0.3 GB，且 80.5 s 比 4 卡的 75.5 s 还慢
- 10 秒档**必须 1 卡**：2 卡 69.8 s 反而慢于单卡 62.4 s
- **1080p 给不到 15 秒**（VAE all-gather 的 fp32 整段视频张量放不下），对外只承诺到 10 秒
- 静态编译**按形状编译**，每个 (宽,高,帧数) 组合各编一次 → 对外只能给固定菜单，且实例启动要预热

### 2.3 两个音频模型

| | MiniMax-Music3 | IndexTTS-2.5 |
| --- | --- | --- |
| 权重目录 | `MiniMax-Music3` | `IndexTTS-2.5` |
| Category | `music` | `text_to_speech`（默认值恰好对） |
| gpus_per_replica | **1** | 1 |
| Backend Parameters | `--deploy-config /usr/local/lib/python3.12/dist-packages/vllm_omni/deploy/minimax_music3.yaml` | `--deploy-config /usr/local/lib/python3.12/dist-packages/vllm_omni/deploy/indextts2_5.yaml` |
| 冒烟基线 | 32 kHz 立体声 27.78 s | 22.05 kHz 单声道 3.99 s（带 ref_audio 克隆） |

### 3.2 运行时配置（**必做**，在 /config → Storage Settings 页）

两张表都是"**先精确匹配、再子串兜底**"（`routes/videos.py::_lookup_by_model`，2026-08-26 修复前是纯
子串+取首个命中，短 key 会静默遮蔽长 key）。

**`lightx2v_model_latency_seconds`（单实例热态延迟标定）** —— 填**稳态**值（见 §3.3，
必须配合启动预热；不预热则第一个请求要多花一个编译周期）：

| 模型（按部署名填） | 建议值 | 依据（服务态稳态实测） |
| --- | ---: | --- |
| LTX-2.5 标准 5 秒（1 卡） | 25 | 24.06 s / 24.32 s |
| LTX-2.5 标准 10 秒（1 卡） | 41 | 40.70 s |
| LTX-2.5 标准 15 秒（4 卡） | 53 | 52.51 s |
| LTX-2.5 高清 5 秒（4 卡） | 48 | 47.38 s |
| LTX-2.5 高清 10 秒（4 卡） | 92 | 91.07 s |
| MiniMax-Music3 | 28 | 27.78 s |
| IndexTTS-2.5 | 4 | 3.99 s |
| **Ideogram-4（2 卡）** | **46** | 45.29 s（官方 schema）/ 44.50 s（简化格式） |
| **SenseNova-U1.5（2 卡）** | **14** | 13.68 s |
| **Krea2（1 卡）** | **14** | 13.68 s |

**`lightx2v_model_queue_wait_seconds`（per-model 队列上限，覆盖 per-kind 默认）**：

per-kind 默认值是 image 25 s / video 150 s / music 90 s / audio 60 s。

- **LTX-2.5 全部档位用默认 150 s 即可**。此前按离线数字（高清 10 秒 143 s）判断"逼近上限、必须调到
  300"，服务态稳态实测是 **91 s**，`floor(1/1)×91 = 91 < 150`，队列里排 1 个仍可接纳，第 2 个才拒。
  若希望高清档能排更深的队，再单独调高。
- **Ideogram-4 必须单独配队列上限**：稳态 **45.3 s**，超过 image 档 25 s 的默认值，
  `floor(1/1)×45 = 45 > 25` → **第二个并发请求会被直接 429**。建议配 **90**（允许队列里排 1 个），
  与 HunyuanImage-3.0 配 110 是同一类处理。
- **SenseNova-U1.5 与 Krea2 用默认 25 s 即可**：稳态均为 13.68 s，`floor(1/1)×13.68 = 13.68 < 25`。

Music3（28 s < 90 s）与 IndexTTS-2.5（4 s < 60 s）用默认值即可，不用配。

### 3.3 服务态实测：编译代价、稳态耗时、预热必要性（2026-08-28）

`vllm serve` + `/v1/videos/sync` 连发请求实测：

| 档位 | 卡数 | 首次（含该形状编译） | **稳态** | 编译代价 |
| --- | ---: | --- | --- | --- |
| 5 秒 960×544 | 1 | 48.07 s | **24.06 s** | ~24 s |
| 10 秒 960×544 | 1 | 65.09 s | **40.70 s** | ~24 s |
| 15 秒 960×544 | 4 | 76.67 s | **52.51 s** | ~24 s |
| 1080p 5 秒（两阶段） | 4 | 103.97 s | **47.38 s** | ~57 s |
| 1080p 10 秒（两阶段） | 4 | 144.36 s | **91.07 s** | ~53 s |

三条结论：

1. **稳态比离线实测快得多**。离线报告里的数字（44.3 / 62.4 / 75.5 / 100.0 / 143.3 s）**全部含首次编译**，
   虚高一个编译周期。生产延迟标定要用本表的稳态值。
2. **编译缓存按形状全部保留**，不是只留最近一个 —— 实测跑完 249 帧后回切 121 帧，耗时 24.32 s
   与首轮稳态 24.06 s 一致，没有重编译。**多档位混合流量不会反复付编译代价**。
3. **两阶段档的编译代价约为一阶段的两倍**（~55 s vs ~24 s），因为要编译两个 stage 的形状。

**图像模型无需预热**：三个图像模型的首次与稳态几乎无差（Krea2 13.88→13.68 s、
SenseNova 15.29→13.68 s、Ideogram-4 44.81→44.54 s），它们走默认的 dynamic 编译，不按形状重编。

**静态编译对图像模型无效**：给 Ideogram-4 加 `--no-diffusion-compile-dynamic` 后是
44.78 / 44.50 s，与 dynamic 的 44.81 / 44.55 / 44.54 s 完全一致。**LTX-2.5 那 1.6~1.9× 的收益
不能外推到其他模型** —— 它的瓶颈在 DiT 的重复 block（regional compile 的作用对象），
Ideogram-4 的瓶颈不在那里。

**预热是必须的**（待办 #4 已验证，仅限 LTX-2.5）：菜单里每个 (宽,高,帧数) 组合在实例启动后各发一次预热请求，
否则每个形状的第一个真实用户要多等 24~57 秒。

## 4. gpustack-ui 侧适配项

### 4.1 部署命名有硬约束（视频体验区按名推断任务类型）

`src/pages/playground/video/task-inputs.ts` 的 `inferVideoTaskType()` 按**模型名 token** 推断任务类型，
命中顺序为：`infinitetalk|s2v` → `seedvr|-sr|结尾sr` → `v2a|dub` → `vace` → `bernini` →
`ref2va` → `fl2va` → `flf2v` → `i2v` → 兜底 `t2v`。

对 LTX-2.5 的含义：

- 部署名**不能含** `v2a` / `dub` / `sr` / `vace` / `s2v` 等 token，否则被误判成别的玩法。
  注意现网已有一个 LTX-2.3 的**视频配音**部署（`ltx2-v2a`），两者要能区分开。
- 建议命名：`ltx2.5-t2v-540p-5s` 这类。图生视频档命名含 `i2v` 会被正确推成 `i2v` ✓。
- 显式的 `meta.task_type` 永远压过按名推断，这是更稳的做法。

### 4.2 图像 / 音乐 / 语音体验区

这三类由 GPUStack 模型列表 + `categories` 驱动，**Category 填对即可出现**，无需改前端代码
（前提是 §1 的 Category 已正确设置）。

### 5.4 ⚠️ 时长口径不一致 —— **已实测确认，必须写代码**

对外体验区/API 说的是**整数秒**，而 LTX-2.5 的引擎侧只接受 **`num_frames = 8k + 1`**。

**2026-08-28 服务态实测（`vllm serve` + `/v1/videos/sync`）**：

```text
POST /v1/videos/sync  -F seconds=5
→ HTTP 500  "LTX2DistilledOneStagePipeline `num_frames` must be 8 * k + 1, got 120."

POST /v1/videos/sync  -F seconds=5.04
→ HTTP 400  seconds 的正则是 ^[1-9]\d*$，只接受整数秒
```

而且这不是"挑个合适的秒数就能绕过"——**在 24 fps 下任何整数秒都无解**：
`frames = seconds × 24`，24 本身能被 8 整除，所以 frames ≡ 0 (mod 8)，永远取不到 8k+1 需要的余数 1。
（`seconds × fps ≡ 1 (mod 8)` 要求两者都是奇数；25 fps 下最小解是 9 秒 = 225 帧，同样不实用。）

**结论：`seconds` 参数对 LTX-2.5 完全不可用，门面层必须显式下发 `num_frames`**，映射表：

| 对外时长 | `num_frames` | 实际时长 |
| --- | ---: | --- |
| 5 秒 | **121** | 5.04 s |
| 10 秒 | **249** | 10.375 s |
| 15 秒 | **361** | 15.04 s |

**落点已确定：new-api**。理由与精确位置：

- GPUStack 侧只是把 `task.params` 原样发给引擎（`routes/videos.py:1509` `engine_body = dict(task.params or {})`），
  这层是模型无关的，塞模型专属映射表不合适。
- gpustack-ui 侧完全没有帧数换算逻辑（全仓搜不到 `num_frames`/`target_video_length`）。
- new-api **已经有同样的换算**，只是口径不对：`relay/channel/task/gpustackplus/adaptor.go:489`
  ```go
  body["target_video_length"] = durationSec*16 + 1   // Wan/LightX2V 的 4k+1 @16fps 约定
  ```
  LTX-2.5 是 **24 fps、8k+1**，同一个公式换个 fps 就成立：`num_frames = durationSec*24 + 1`。
  而且 24 能被 8 整除，所以 `durationSec×24+1` **恒满足 8k+1**，对任意整数秒都成立：

  | 对外时长 | `num_frames` | 实际时长 |
  | --- | ---: | --- |
  | 5 秒 | **121** | 5.04 s |
  | 10 秒 | **241** | 10.04 s |
  | 15 秒 | **361** | 15.04 s |

  （本报告 §3.3 的 10 秒档实测用的是 249 帧 = 10.375 s；按统一公式应取 **241**，两者都合法，
  241 更贴近"10 秒"这个对外口径，延迟略低于实测的 40.70 s。）

**改法照抄 MiniMax-H3 的现成模式**（三处，都是加，不改既有行为）：

1. `common/media_model_config.go:444` 旁边加引擎族常量：`const VideoEngineLTX25 = "ltx-2.5"`
2. 新建 `relay/channel/task/gpustackplus/ltx25.go`，仿 `minimax_h3.go` 写 `applyLTX25Request()`
3. `adaptor.go:474-491` 加分支：识别到 LTX-2.5 引擎族时走 `num_frames`，**跳过**默认那条
   `target_video_length = durationSec*16+1`

引擎族的判据是**配置声明**（`VideoModelConfig.models[<模型名>].engine = "ltx-2.5"`），
不是模型名 substring —— 这条是 `media_model_config.go:446` 注释里点名的踩过的坑：
前端拿对外模型名、后端拿渠道重定向后的上游名，靠名字判断两边必然分叉。

### 5.4b Ideogram-4 提示词层设计（网关层，2026-08-29 实测定稿）

#### 实测：机械包装无效，必须真的做语义分解

同一批自由文本，三个变体各跑一遍（1024×1024，`/v1/images/generations`）：

| 变体 | 做法 | 正常率 |
| --- | --- | --- |
| A raw | 纯自由文本直接发 | **2/6** |
| B minimal | **纯机械包装**：自由文本原样塞进 `high_level_description` + 一个全画布 element，`style_description` 用固定默认值 | **3/6** |
| C full | 人工把画面拆成多个 element，各带 `bbox`/`desc`/`color_palette` | **2/2** |

逐条数据：

| case | A raw | B minimal | C full |
| --- | --- | --- | --- |
| lighthouse | BLOCKED (std 9.68) | BLOCKED (std 18.34) | OK (std 50.07) |
| windmill | BLOCKED (std 9.74) | OK (std 59.62) | OK (std 58.67) |
| subway | OK (std 55.32) | OK (std 66.13) | — |
| bakery | OK (std 44.71) | BLOCKED (std 18.43) | — |
| desert | BLOCKED (std 9.50) | OK (std 49.84) | — |
| hummingbird | BLOCKED (std 9.56) | BLOCKED (std 18.45) | — |

**B 档 2/6→3/6 在噪声范围内，等于没用。** 起作用的是"真的把画面拆成带位置的元素"，
不是"套上 JSON 外壳" —— 加上 §A.5 那次 lighthouse 与报告里的 18/18，语义分解的证据是一致的。

**所以自由文本用户必须走 LLM 改写，机械模板兜不住。**

#### 四条处理路径（全部在网关层，引擎层不动）

| # | 入参形态 | 网关做什么 |
| --- | --- | --- |
| 1 | prompt 已是官方 schema JSON | **原样透传**。识别：能解析成 JSON 且含 `high_level_description` 或 `compositional_deconstruction` |
| 2 | API 直连、调用方自己传元素 | 网关按官方 schema 组装。新增可选入参（如 `extra.elements[]` + `extra.style_description`），**把摆位自由留给调用方** |
| 3 | 体验区画布 | 前端可视化摆 bbox → 直接生成官方 schema → 走路径 1 透传 |
| 4 | 纯自由文本 | **LLM 改写**成官方 schema（实测证明机械包装无效） |

**引擎层不做转换**：做进 vllm-omni 就把格式焊死了，调用方再想自己控制构图反而没自由度。

#### 画布规格（体验区）

参考实现：社区插件 `ComfyUI-Ideogram4-DirectJSON-Modified`（纯 JSON/bbox 可视化编辑器，
无任何"4 个框解锁"的硬编码，那个说法是误传）。它自带 workflow 里的真实模板确认了官方字段形态：

```jsonc
{
  "high_level_description": "一整段画面描述（不是一句话）",
  "style_description": {
    "aesthetics": "...", "lighting": "...", "photo": "...",
    "medium": "...", "color_palette": ["#1E73BE", "#FDFDFD", "..."]
  },
  "compositional_deconstruction": {
    "background": "背景描述（参考实现里是**字符串**；用对象 {desc,color_palette} 实测也能吃）",
    "elements": [
      { "type": "obj", "bbox": [128, 149, 354, 810],
        "desc": "该元素的完整描述", "color_palette": ["#FDFDFD", "..."] }
    ]
  }
}
```

⚠️ **`bbox` 坐标形态**：官方参考实现用的是**绝对像素**（上例在 1024 画布上取到 810）。
本报告 §A.5 用归一化 0~1 也生效（灯塔准确落在指定的右上区间），两种都能吃，
但**画布应输出像素坐标**以对齐官方。`type` 的取值参考实现里是 `"obj"`。

画布要提供的最小能力：画框、拖拽/缩放、每框填 `desc` 与 `color_palette`、
一个全局的 `high_level_description` 与 `style_description` 表单，导出即官方 schema。
element 数量无硬性要求（报告已验证 1/2/3/4 个都正常）。

#### LLM 改写（路径 4）的落点与现状

落点：`relay/channel/gpustackplus/adaptor.go:180 ConvertImageRequest()`，
第 199 行 `body["prompt"] = request.Prompt` 之前。**同一函数里已有按模型定制 prompt 的先例**
（ERNIE 的 `applyErnieImageTurboDefaults`、HunyuanImage-3.0 的 `hunyuanPromptKeys` 透传），
Ideogram-4 的转换插进同一处即可。

⚠️ **new-api 目前没有"内部调 LLM"的现成设施**（`service/sensitive_refusal.go` 只负责写拒绝响应，
不是模型调用）。需要新建：或 loopback 调自己的 `/v1/chat/completions`（配内部模型名 + 内部 token），
或直连一个上游渠道。这是本项唯一的"从零"工作量。

#### 兜底：拦截检测与计费

被拦的图是一张"纯色底 + `Image blocked by safety filter` 文案"的卡片，统计特征分离得很干净：

- 被拦（6 张）：std **9.5 ~ 18.5**
- 正常（8 张）：std **44.7 ~ 66.1**

取 **std < 30** 作为判定阈值有足够余量（两组间隔 26 个标准差单位）。网关检测到后应
**返回明确错误码而不是把废图交付**。

⚠️ **计费影响**：被拦的请求**跑满全部采样步**，耗时与正常请求一致（44.5 s vs 45.3 s）——
**误拦不省算力，是纯浪费**。按次计费下，被拦请求**不应向用户计费**，否则用户为一张废图付钱。

### 5.5 计费（按次）

现网口径是**按生成次数收费**，一次多少钱，**不按时长/token 计**，**视频自带的音轨也不单独计费**。
六个模型各配一条 `ModelPrice` 即可（价格为 0 一律被视为"未配置"而非"免费"）。

同一模型的不同档位（如 LTX-2.5 的 5/10/15 秒、540p/1080p）如果要差异化定价，
需要拆成不同的对外模型名各配一条，因为按次计费只认模型名这一个维度。

### 5.6 体验区前端文案（可选）

`web/classic/src/constants/` 下的 `videoPlayground` / `musicPlayground` / `audioPlayground` /
`promptGuide` 有按模型的示例与提示词引导。**LTX-2.5 值得补一条**：官方 README 明确写
"模型在长段单段落视听描述上训练，短提示词会明显劣化"，需要在 UI 引导用户写整段
（镜头 / 运动 / 光线 / 声音）。其余模型可后续补。

## 8. 一句话总结

**代码改动集中在 new-api**：三处加 LTX-2.5 的秒→帧换算（照抄 MiniMax-H3 的现成模式），
外加一个 Ideogram-4 的提示词结构化转换层（**上线阻塞项**）。
GPUStack 只有一处可选的 category hints，gpustack-ui 零改动。其余全是运行时配置。

**吞吐参考**（稳态、一机四卡）：LTX-2.5 标准 5 秒档 4 路并发 ≈ **10 条/分钟**；标准 10 秒 ≈ 5.9 条/分钟；
1080p 5 秒（整机一路）≈ 1.3 条/分钟；1080p 10 秒 ≈ 0.66 条/分钟；
Krea2 / SenseNova-U1.5 ≈ 17.5 条/分钟（4 路）；Ideogram-4 ≈ 2.7 条/分钟（2 路，每路 2 卡）。

**最容易漏、且漏了不报错的四件事**：
