## 一、现网是怎么被"纳管"的（合入路径的前提）

| 事实 | 值 | 取证方式 |
| --- | --- | --- |
| 引擎后端条目 | GPUStack `inference_backends` id=14，`backend_name=vLLMOmni`，`default_version=1.0.0` | `docker exec -u postgres gpustack-server psql -d gpustack -c "select ..."` |
| 镜像来源 | **唯一一处**：`version_configs["1.0.0"].image_name = reputationly/vllm-omni:arm64-a100-latest`（浮动 tag） | 同上 |
| 现网镜像 = | `crpi-...aliyuncs.com/reputationly/vllm-omni:arm64-a100-20261103-1149-5623dec5`，digest `8838e733804e`，构建于 2026-11-03 | 节点 `docker images` / `docker inspect` |
| 镜像基座 | `vllm/vllm-openai:v0.31.0`（容器内 `VLLM_IMAGE_TAG`） | 节点 `docker inspect` → env |
| 每模型差异 | 只靠 ① `--deploy-config=/deploy-configs/*.yaml`（**烘进镜像**，不是外挂）② 模型级 `env` ③ `backend_parameters` | `/v2/models`，容器 `Cmd`/`Env` |
| 单模型改镜像 | 支持（`models.image_name` 字段存在）但**现网全部为 NULL**，即没有按模型分叉 | `/v2/models` |

结论：**合入路径只有一条 —— 重出镜像 → 改后端版本的 image → 重启副本**。没有"只给某个模型开某个优化"的配置通道；
新上游优化（FastH3/ref-KV/schedules/sampler/regenerate…）都只能随镜像一起落到现网。

另有一个摩擦点：部署档 `/deploy-configs/*.yaml` 是 `COPY` 进镜像的，**改一行部署参数也要重新出包**。

## 三、本次合并后镜像的已知变化（会影响"不慢/不涨"的判定）

1. **基座 vLLM 0.31.0 → 0.33.0**（upstream 的 `Dockerfile.cuda` 固定到 `vllm/vllm-openai:v0.33.0@sha256:d825baf9…`）。
   arm64 manifest 已确认存在。这是最大的不确定项：影响**所有** vLLMOmni 模型，不只是 H3/qwen-image。
2. H3 侧新增上游能力：FastH3/PDD、reference-KV 缓存（`--kv-offload-config`）、per-step attention schedule、
   跨请求 latent cache/续写、Open-H3-Regenerate-2K、ControlNet-Union、LiteVAE、以及 H3-Image 出图。
   均需部署档或参数**显式开启**，默认不会改变现网行为。
3. H3 采样框架换成 `vllm_omni/diffusion/sampler.py`：本仓的 Pika `renoise` 已重新表达为
   `sample_renoise`（每请求独立 `torch.Generator`，经 `sampler_object(name, generator=…)` 传递），
   `euler`/`res_multistep` 与上游逐字节一致。
4. 本仓定制（须在验收里逐项确认）：fl2va canvas buckets / `source_center_crop` keyframe、参考图总像素预算、
   conditioning-numerics（RNG）契约、VDN_WINDOW_ATTN（与上游 VDNH3_ATTN 并存）、pruned-AdaLN/folded-bias、
   int8 文本编码器档、offload CPU-home 复用、异步任务 phase/progress 上报。

## 四、上线流程（建议）

```
1) 出包（已完成一次）:
   gh workflow run build-arm64.yml -R reputationly/vllm-omni \
     --ref merge/upstream-20261114 \
     -f base_image=vllm/vllm-openai:v0.33.0 \
     -f dest_tag=arm64-a100-merge-20261114        # 不要直接推 latest
   产物: reputationly/vllm-omni:arm64-a100-<UTC 时间>-b957c72f（不可变）+ :arm64-a100-merge-20261114
2) 金丝雀: 在 1–2 台空闲 A100 上手工起同一份部署档的新镜像容器（不接流量、不进 GPUStack），
   用 bench/prod-baseline-20261114/requests/ 里的同一请求跑 3 次，逐 phase 对比 + nvidia-smi 峰值对比。
3) 注册新后端版本: inference_backends id=14 的 version_configs 增加 "1.1.0" -> 新镜像 tag；
   现网模型仍指向 1.0.0（可回滚）。
4) 逐模型迁移: 先把 minimax-h3-fl2va 的 10 个副本迁到 1.1.0（滚动重启），观察一轮；
   再 ref2va、qwen-image-pro、minimax-music3、indextts-2.5。
5) 全绿后把 arm64-a100-latest 指到新不可变 tag（或直接改 version_configs 的镜像并保留旧 tag 做回滚）。
```

## 五、验收门（硬指标，按用户要求）

| 指标 | 门限 | 采集方式 |
| --- | --- | --- |
| 端到端耗时 | 每个模型、每个副本 3 次的**中位数** ≤ 现网基线中位数 × 1.00 | 同一请求体、同一 seed、并发 1 |
| 分阶段耗时 | prepare/encode/denoise/decode 任一 phase 不得明显劣化（>5% 需解释） | `/v1/tasks/{id}/status` 的 phase 字段 |
| 显存 | 4 卡 `memory.used` 峰值（求和）≤ 基线峰值；且不得出现 OOM/重试 | 请求期间 2s 采样 `nvidia-smi` |
| 产出正确性 | 帧数/尺寸/时长与基线一致；同 seed 两次重跑一致（renoise 抽样） | 输出元数据 + 逐帧 sha256 |
| 稳定性 | 连续 20 次请求无失败、无 EngineDead | 容器日志 + 任务状态 |

## 六、回滚

`version_configs` 保留 1.0.0 → `arm64-a100-20261103-1149-5623dec5` 的不可变 tag；单模型回滚只改 `backend_version` 再重启副本。
