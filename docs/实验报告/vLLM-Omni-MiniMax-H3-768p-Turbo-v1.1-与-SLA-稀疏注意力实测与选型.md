# MiniMax-H3 768p 档：Turbo v1.1 与 SLA 稀疏注意力实测与选型

> 实验日期：2026-08-20 ~ 08-21　机器：dev-gpustack-a100-0041 ~ 0045（各 4×A100-PCIE-40G）
> 结论一句话：**768p 档换 `fl2v_turbo_4step_v1.1_768p`（画质三个用例全胜、速度显存持平）；SLA 稀疏注意力已接通且加速真实（15 秒档 −23%），但暂不上线**——稀疏率必须随片长变、动画类画质与稳定度仍不及 v1.1、backend 未进主干。

---

## 1. 背景与本轮做了什么

2026-08-20 上游 `lightx2v` 同一天发了两样东西：主线仓的 `minimax_h3_fl2v_turbo_4step_v1.1_768p_bf16`，以及独立仓 `Minimax-h3-Turbo-SLA` 的 `..._v0.1_768p_sla_bf16`。两者都没有 release note。本轮回答三个问题：

1. v1.1 相对线上的 v1.0 值不值得换；
2. SLA 那份是什么、能不能用；
3. 让两份权重各自跑在被设计的路径上（v1.1 走稠密、SLA 走稀疏）之后，如何取舍。

为此新写了一个 SLA 块稀疏 attention backend（§6），并在五台机上跑了 60 余次生成。

---

## 2. 权重层面的事实（不依赖上游说法）

两份新权重与 v1.0 结构完全同构：624 tensors / transformer_blocks 50 / refiner 2 / rank 128 / alpha 128 → **融合缩放 1.0**，字节数同为 1,383,677,808。SLA 那份没有任何稀疏专属参数——`thu-ml/SLA` 的 `proj_l` 是零初始化的线性分支，LightX2V 自己的 `dynamic_sparse_attn` 干脆不实现它，所以**加速全在 kernel 里，权重只是"被训练成能容忍稀疏"**。

312 对 A/B 因子逐个算有效更新量 ΔW=B@A 的余弦：

| 配对 | 余弦中位数 | 范数比中位 |
|---|---|---|
| SLA v0.1 ↔ v1.1 | **0.956** | SLA 大 5% |
| v1.0 ↔ v1.1 | 0.885 | v1.1 大 16% |
| SLA v0.1 ↔ v1.0 | 0.830 | SLA 大 22% |

**SLA 离 v1.1 比 v1.0 离 v1.1 还近**：它是从 v1.1 那一代检查点上做的 SLA 微调，文件名里的 `v0.1` 是 SLA 变体自己的计数，不是 mainline 老 v0.1 的血统。v1.1 相对 v1.0 则是同配方继续训练——方向一致（0.885）、幅度普遍大 16%、没有一层是原样搬过来的。

烘焙与组装（`bake_turbo_lora.py` + `assemble_distilled_partition.py`）：

| | v1.1 | SLA v0.1 |
|---|---|---|
| patched | 208 tensors | 208 tensors |
| ‖Δ‖/‖W‖ 中位 | 0.0015 | 0.0016 |
| 逐张量验真 | `max_abs_error 0.0`，312 因子对 / 208 目标全过 | 同 |
| changed_values | 3,311,777 | 3,444,480 |
| 产物 | `MiniMax-H3-FL2VA-Turbo4-768p-v1.1-BF16-vLLM` | `...-SLA-v0.1-BF16-vLLM` |

两者都是 4 NFE、shift 6/3、`base_schedule = [1, .75, .5, .25, 0]`。

## 3. 方法与已控住/未控住的变量

**用例**（全部 1344×768、seed 42、同一份引擎代码）：

| 用例 | 任务 | 时长 | 说明 |
|---|---|---|---|
| `daimaru768` | t2va | 15s | 「动画大丸家」fmt3 优化提示词，3399 字符，分镜结构 + 身份锁定 |
| `boars768` | fl2va | 5s | 手绘动画，两张参考图（首尾帧） |
| `rooftop768` | t2va | 5s | 官方示例，真实拍摄质感 + 复杂音轨 |

**控住的**：同 seed、同提示词、同输入图、同引擎代码与启动参数（TP4 / usp 1 / ring 1 / regional compile）、同 partition 元数据。

**控住得晚的（重要）**：前半程 A/B/C 各跑在 0041/0042/0043 三台不同机器上，导致把机器差异误读成权重差异。用 2×2 交叉实验修正后（§5.1），机器效应 7~8%、权重效应 ≈0。**此后所有对比都是同机、剔除冷启动首发、取稳态多发平均。**

**没测的**：音频内容（现有 e2e 只校验 aac/32000Hz/2ch 容器属性）；主观画质（本报告只出客观代理指标，不做截图/宫格）；ref2va 链路（本轮全部是 FL2VA partition，两个 t2va + 一个 fl2va，ref2va 零覆盖）。

## 4. 五档基线对比（v1.0 / v1.1 / SLA-dense / Turbo8 / 满血）

⚠️ 这一组是各档跑在不同机器上的单发数据，**耗时含 ±8% 的机器差**，仅用于看数量级；权重结论以 §5 起的同机数据为准。

| 用例 | A v1.0 4步 | B v1.1 4步 | C SLA 4步 | D turbo8 8步 | E 满血 20步 |
|---|---|---|---|---|---|
| daimaru768 15s | 213.3s | 217.6s | 229.3s | 400.1s | 886.8s |
| boars768 5s | 72.4s | 75.3s | 91.7s | 118.0s | 238.6s |
| rooftop768 5s | 64.5s | 67.0s | 75.6s | 110.5s | 212.5s |
| 峰值显存（15s） | 34.3 GiB | 34.3 GiB | 34.3 GiB | 34.4 GiB | 35.8 GiB |

4 步档相对满血 20 步：15 秒 **4.2×**、5 秒 3.3×；8 步档 2.2× / 2.0×。**片长越长加速比越高**——固定开销（文本编码、VAE、封装）被摊薄。

以满血 20 步为参考的 SSIM（越高越接近满血）：

| 用例 | A v1.0 | **B v1.1** | C SLA-dense | D turbo8 |
|---|---|---|---|---|
| boars768 | 0.8774 | **0.8900** | 0.8601 | 0.9044 |
| daimaru768 | 0.5871 | **0.6453** | 0.6401 | 0.6674 |
| rooftop768 | 0.7349 | **0.7648** | 0.7642 | 0.8146 |

**v1.1 在三个用例上全部优于 v1.0**，而耗时与显存和 v1.0 无差别。8 步的 turbo8 最接近满血（意料之中，步数多一倍），代价是慢 1.9 倍。

## 5. 三个被推翻或修正的结论

### 5.1 「SLA dense 比 v1.1 慢 7~27%」——是机器差异，不是权重

2×2 交叉设计（0042/0043 各跑两份权重、每份每用例 3 发、剔除首发）：

| | boars768 | rooftop768 |
|---|---|---|
| 0042 + SLA / 0042 + v1.1 | 69.05s / 66.30s | 60.75s / 58.90s |
| 0043 + SLA / 0043 + v1.1 | 71.00s / 75.05s | 62.00s / 66.55s |
| **机器效应** | 0043 慢 **+7.9%** | 0043 慢 **+7.4%** |
| **权重效应** | SLA **−0.9%** | SLA **−2.2%** |

机器间稳定差 7~8%，权重间只有 −1~−2%（方向还偏 SLA），落在噪声内。这与机制一致：架构、步数、张量形状全同，DiT 的 FLOPs 就是一样的。**教训：跨机单发数据不能用于权重级结论。**

### 5.2 「Turbo8 音频电平失控」——基座本身就削波

15 秒 daimaru 档五档的音频真峰值：A **+1.5**、B **+0.7**、C **+0.7**、D **+2.2**、E **+0.9 dBFS**。**满血基座（E）同样削波**。所以 −1 dBTP 限幅是所有档位都要在门面层统一加，不是 Turbo 专属补丁。

### 5.3 「#37 同 seed 产物不确定」——是实例级，不是请求级

同一引擎实例内的稳态多发**逐字节相同**（sha256 一致）；但换机器或换实例后，同 seed 同权重出的字节就不同；且实例加载后的**首发结果与稳态结果不同**。

```
boars768 + v1.1 :  0042 → 3829d2af…    0043 → 1d0bbd83…
boars768 + SLA  :  0042 → 6d1ef4ac…    0043 → 1e93aba5…
```

指向进程/机器状态（很可能是 kernel 自动调优或 compile 选择），不是采样随机性。**同实例可复现、跨实例不可复现**是排查 #37 的收敛方向。另外首发墙钟是稳态的 2 倍（150.9s vs 68.2s），压测取数必须丢弃首发。

## 6. SLA 稀疏注意力接入

### 6.1 实现

新增 `vllm_omni/diffusion/attention/backends/sla_attn.py`，复用仓内既有的块稀疏契约：`BlockSparseSpec`（`sparsity` / `start_step` / `skip_layers`）、注册表加 `SLA_ATTN`、平台侧缺包退回 FlashAttention。**模型代码一行未改**——H3 早已发布 `VideoTokenLayout`、声明 `qkv_layout="BSND"`、并在 `AttentionMetadata.extra` 里带 `cu_seqlens` / `max_seqlen` / `valid_kv_length`，这套契约本就是给块稀疏 backend 准备的（`rainfusion_attn.py` 是同一形状的 NPU 先例）。

两处与参考实现的有意差异，已写在模块 docstring 里：跳过恒零的线性分支（与 LightX2V 一致）；块选择覆盖整个 packed 序列而不豁免 prefix（与上游蒸馏时的注意力模式一致）。

选择由 `--diffusion-attention-config` 显式开启，默认仍是 FlashAttention，**不配就等于这段代码不存在**。

### 6.2 生效验证

引擎自打的日志（只认引擎日志，不认 tag/env）：

```
SLA_ATTN active: sparsity=0.85 (keeps 98 of 654 key blocks), rows=41827      ← 5 秒档主干
SLA_ATTN active: sparsity=0.70 (keeps 514 of 1716 key blocks), rows=109795   ← 15 秒档主干
SLA_ATTN staying dense: 76 rows is 2 key blocks, under the 32-block threshold ← token_refiner 自动退回
```

单测 11 项全过，最关键一条：**稀疏率设为 0 时输出与稠密 SDPA 在 2e-2 内一致**，证明布局、缩放、进出转置接线正确；85% 稀疏下输出改变且全部有限；padding 行为零。

### 6.3 结果：5 秒档（0043 单机，稳态）

| | boars768 墙钟 / 去噪 | rooftop768 墙钟 / 去噪 | 显存 |
|---|---|---|---|
| **SLA + 稀疏 0.85** | **67.3s / 45.1s** | **59.1s / 39.1s** | 30.2 GiB |
| SLA + 稠密（错配） | 71.0s / 50.1s | 62.0s / 45.1s | 29.9 GiB |
| v1.1 + 稠密 | 75.0s / 52.1s | 66.5s / 46.1s | 29.9 GiB |

稀疏比 v1.1 稠密快 10~11%（墙钟）、13~15%（去噪段）。**稀疏只作用于去噪，VAE 与封装不受益**，所以墙钟收益被摊薄。

### 6.4 稀疏率扫描（0042 单机，5 秒档）

| | boars768 墙钟 / SSIM | rooftop768 墙钟 / SSIM |
|---|---|---|
| v1.1 稠密（基线） | 68.7s / **0.8900** | 60.8s / 0.7633 |
| SLA 0.5 | 72.9s / 0.8617 | 63.3s / 0.7772 |
| **SLA 0.7** | **65.5s / 0.8635** | **56.8s / 0.7779** |

**0.5 是纯亏**：比 0.7 还慢，画质也不占优。稀疏率低意味着保留块多，而**块选择的固定开销（池化、top-k、建 LUT）一分不少**，算的量接近稠密却比高度优化的 FlashAttention 慢。0.7 在 5 秒档支配 0.5。

### 6.5 结果：15 秒档（0043 单机，稳态）

| | 墙钟 | 相对 v1.1 | SSIM | 闪烁 YDIF_std |
|---|---|---|---|---|
| **SLA 稀疏 0.85** | **174.6s** | **−23%** | 0.6293 | 9.324 |
| SLA 稀疏 0.70 | 213.9s | −5.6% | 0.6362 | 9.689 |
| v1.1 稠密 | 226.6s | 基线 | **0.6450** | **8.477** |

**稀疏率的最优值随片长变**：5 秒档 0.7 最好，15 秒档 0.85 最好。序列变长后 block 数从 654 涨到 1716，选择的固定开销被摊薄，高稀疏率才划得来。这意味着上线不能配一个全局常数。

### 6.6 SLA 相对 v1.1 的净收益

| 场景 | 加速 | SSIM 代价 | 闪烁代价 |
|---|---|---|---|
| 5 秒手绘 fl2va | −10% | −0.050 | +27% |
| 5 秒真实 t2va | −11% | **+0.024（更好）** | +2% |
| 15 秒动画 t2va | **−23%** | −0.016 | +10% |

显存全程多 0.3 GiB。**优势只有速度一项，且只在长片上值一提；动画类的画质与稳定度始终不及 v1.1。**

## 7. 上线配置决策

### 7.1 立即执行

**768p 档：把 Turbo4 从 v1.0 换成 v1.1。**

- 依据：SSIM 三个用例全胜（+0.013 / +0.058 / +0.030），耗时与显存无差别（交叉验证后权重效应 ≈0），血统在主线上。
- 模型路径：`/nfs-data/models/MiniMax-H3-FL2VA-Turbo4-768p-v1.1-BF16-vLLM`
- deploy-config：**复用 `/deploy-configs/minimax_h3_a100_40g.yaml`，不要新建**（权重路径不在 yaml 里，步数是请求级的）。
- new-api：模型级 `defaultSteps: 4`。不配的话请求不带步数，会跑 yaml 默认的 20 步，加速全丢。
- 六个 `VLLM_OMNI_*` 环境变量照配（见生产部署档），少一个都不行。
- 上线前必须人工看片确认（本报告只给客观指标）。

**门面层统一加 −1 dBTP 限幅。** 15 秒档五档全部削波（含满血基座），这不是 Turbo 权重的问题，是全链路问题。

### 7.2 暂不上线

**SLA + 稀疏注意力**。三个理由，按重要性排：

1. **稀疏率必须随片长变**（5 秒 0.7、15 秒 0.85），配一个常数会在另一端亏掉；要上线得先做成按序列长度选值，并覆盖更多档位（10 秒、480p、ref2va）。
2. **动画类画质与稳定度不及 v1.1**，而动画促宣片是当前主力场景。15 秒档 SSIM 差 0.016 看似小，但闪烁高 10%，这一项对动画观感的影响通常比 SSIM 大，必须先人工看片。
3. **backend 尚未进主干**，当前是 PYTHONPATH 叠加 + NFS 引入 SLA 包起的实验态；进生产要么打进镜像，要么按纳管实例的规矩固化（容器内 hot-patch 会随重建丢失）。

**保留价值**：加速是真实的（15 秒档 −23%，是这轮唯一能把 15 秒片拉进 3 分钟内的手段）。**触发条件**：当 15 秒档吞吐成为瓶颈、或需要在同样卡数下多接一倍并发时，把它作为独立档位上线，而不是替换 v1.1。

### 7.3 不变

- **480p 档继续用 Turbo8**：它的训练分辨率在 544p，且是唯一有现网数据的档（1.68~1.93×、锐度 8 用例全胜）。本轮 768p 上 turbo8 慢 1.9 倍、无优势，但那不是它的主场。
- **满血 20 步作为画质档保留**，它是所有 SSIM 的参考基准。
- **ref2va 链路本轮零覆盖**，其 Turbo4 v0.1 仍是「已烘、未压测」，结论不能从本报告外推。
