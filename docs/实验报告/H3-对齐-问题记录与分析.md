run-id `align01`。按"现象 → 证据 → 根因 → 影响 → 处置"记录。
证据一律给可复核的绝对路径或命令，不写"看起来"。

最近更新：2026-08-16

## 一、测量方法问题（同一类根因，踩了三次）

### P-M1 旧 harness 的短边 env 从未生效

**现象** `runcap.sh` 里 `-e VLLM_OMNI_H3_REF_IMAGE_SHORT_EDGE=768`，但改这个值对结果无影响。

**证据** 镜像内 `pipeline_minimax_h3.py` 只有写死的常量：

```
docker exec <c> python3 -c "from vllm_omni...pipeline_minimax_h3 import _reference_image_short_edge"
→ ImportError: cannot import name '_reference_image_short_edge'
docker exec <c> python3 -c "... print(p.MINIMAX_H3_REFERENCE_IMAGE_SHORT_EDGE)" → 2048
```

**根因** 镜像 `arm64-a100-latest`（digest 45fd694e66e4）落后仓库 HEAD 两个 H3 提交
（`99530748`、`226dd901`），env 开关是这两个提交才引入的。旧实验之所以看似生效，
是因为它们额外挂载了 `/nfs-output/h3_patch/pipeline_minimax_h3.py`（含开关的补丁文件）。

**影响** 现网镜像上这三个 env（`REF_IMAGE_SHORT_EDGE` / `NO_UPSCALE` / `MAX_PIXELS`）
**全部是死开关**。任何"调小短边省显存"的运维预案在当前镜像上都不成立。

**处置** 已改为显式挂载：要测 HEAD 行为就挂 HEAD 的 `minimax_h3/` 目录（gpu39 验证
引擎可正常起，380s 就绪），要复现旧实验就挂 `h3_patch`。不需要出新镜像。

---

### P-M2 `docker logs --since` 的时区陷阱

**现象** 不同输入的用例报出完全相同的 `rows video=`。

**根因** `date -u +%FT%T` 产生的时间戳不带时区后缀，docker 按**本地时区**解析。
UTC+8 主机上传 UTC 戳 = 窗口前移 8 小时，`head -1` 于是稳定返回该容器**第一发**请求的行。

**处置** 弃用 `--since`。改为提交前统计已有匹配条数 `PRE`，本次取第 `PRE+1` 条。

---

### P-M3 未等终态就采集

**现象** 修掉 P-M2 后，`probe_one`/`probe_n` 的连续用例仍然全部相同。

**根因** 这两个脚本一读到 rows 就退出，不等请求进入终态。下一发计算 `PRE` 时，
上一发仍在写日志（每步 × 每 rank 各一行，4 步 4 卡 = 12 行），于是 `PRE` 偏小、
`PRE+1` 落进上一发的行里。

**处置** 统一走 `req.sh`（等 `completed|failed|cancelled` 才返回）。
`probe_*` 的全部结论已作废重测。

---

### P-M4 身份守卫锚在一个每次调用都会变的值上

**现象** 隔离矩阵两臂提交请求全部被自己的守卫拒绝：

```
!! INVALID: port 41033 serves 'modelperm-bf709ce…' but geoonly's identity says 'modelperm-b15c…'
```

**根因** 守卫比对的是 `/v1/models` 返回的 `modelperm-*`。该 id **每次请求现生成**：
对同一个未重启的容器连查两次，得到 `bf709ce…` 与 `ba941b7…` 两个不同值。
identity 文件之所以"当时是对的"，只是因为它就是用那一次调用的返回值写的。

于是这道守卫**永远不可能通过**。而一个恒假的守卫和一个恒真的守卫一样没有信息量 ——
它不保护任何东西，只是把实验挡在门外。

**处置** 改锚在真正稳定、且实验真正依赖的事实上（`req.sh`）：

1. 容器在跑（`--network host`，容器名唯一决定端口归属）；
2. 端口确实在服务 MiniMax 模型；
3. 启动时打的 **contract 行**与 identity 记录一致 —— **不一致即致命**；
4. 容器 id 变了但 contract 一致 → 只是重启过，记一行 note 并刷新 id，继续。

**与 P-M0 的关系** P-M0 说"不要相信来源未经核实的值"。这次是同一原则在守卫**自身**
上的失守：我核实了"这个值属于谁"，却没核实"这个值是否稳定到可以跨次比较"。
判据要补一条：**用作身份锚点的量，必须先证明它对同一对象的重复观测是恒定的。**

### P-M5 引擎跑的是镜像原版代码，而 tag / env / 日志三处都说不是

**现象** `geoonly` 臂（legacy 契约 + official 几何）跑完 1131s，出片正常，但：

- `rows video=115024` —— 这是 **legacy 几何**的行数指纹，期望值是 118224；
- `docker logs` 里一条 `MiniMax-H3 contract:` 都没有（该行只有补丁代码会打）。

**根因（两层）**

1. `serve.sh` **从来不挂改动代码**。上一轮会话是用手写的带 `-v` 的 `docker run`
   起的引擎，挂载没有沉淀进 harness。我用 `serve.sh` 重启，就只剩 NFS 数据卷，
   容器安静地跑起了镜像原版 —— 原版能正常加载、正常出片、正常回 200，
   **readiness 不能证明任何关于"跑的是哪份代码"的事**。
2. 我本次会话开头那条 `rm -rf vllm_omni tests && tar xzf -` 删掉了正在被 4 个
   运行中容器 bind-mount 的目录。bind mount 认的是 **inode**，重建目录后旧容器
   拿到的是 `Stale file handle`：

   ```
   ls: cannot access '.../minimax_h3/strategy.py': Stale file handle
   ```

   这同样是静默的 —— 已 import 的模块留在内存里照常工作，只有**新的**文件访问会失败。

**影响判定（逐台核过，不是推测）**

| 引擎 | 启动时机 | contract 行 | 结论 |
|---|---|---|---|
| abOFF / rngonly / legvar / offvar | `rm -rf` 之前，带代码挂载 | 4 | 补丁代码已入内存，**已采结果成立** |
| geoonly / se1024 | `rm -rf` 之后，经 serve.sh | 0 | **跑的是原版，结果作废** |

rngonly 那一发全程无 import 失败并正常完成，故其 115024 rows 的结论不受影响。

**处置（两处都落在 harness 里，不靠人记得）**

1. `serve.sh` 现在**强制**挂 8 个改动文件/目录，源文件缺失即拒启动（exit 5）；
   就绪后再 `docker exec test -f strategy.py`，不通过就删容器并 exit 6 ——
   同时覆盖"没挂代码"与"挂了但 handle 已失效"两种情况。
2. 同步改为 `h3sync.sh`：**原地覆盖，绝不 `rm -rf` 目的目录**，保住 inode 与挂载。

**与 P-M0 / P-M4 的关系** 同一根因的第三种形态。P-M0 是"这个数属于谁不明"，
P-M4 是"身份锚点本身不稳定"，这次是"身份锚点根本没被检查——因为没人想到要
检查代码"。补充判据：**一次运行必须能自证它跑的是哪份代码**；tag、env、日志文件名
都是人写的标签，只有引擎自己打出的、只有新代码才会打的那行才算证据。

### P-M6 产物留下了，但生成它的请求没留下

**现象** 用户问 `abLEG/a7-face-seed43.mp4` 为什么和 `a6-face-front-15s.mp4` 差异巨大。
查下来 a7 换了**提示词**（白色影棚、锁定机位、脸部占满画面）**又换了 seed**（43 vs 42），
两者本就没有可比性。但真正的问题在 a6 一侧：

**`abLEG` / `abOFF` 的 a6 日志里没有请求体** —— 这两条跑在 req.sh 加入
"记录 request body" 之前。提示词无处可查：

- 任务日志没记；
- 引擎日志只打 `encode_prompt took 6.1s`，不打文本；
- 节点是非交互 SSH，**没有 shell 历史文件**。

于是这两个 mp4 **永久失去了可比性**：文件还在，但没人能证明它是用什么请求生成的。

**连带的错误** 我据此列过一张六臂对照表，把今天新跑的四条与 abLEG/abOFF 并排。
今天四条彼此可比（都有完整请求体），但**与 abLEG/abOFF 并列没有依据** —— 我默认了
它们用同一个提示词，而这一点无法证实。这是"用了来源未经核实的值"在**对照组**上的
重演。

**处置** 用两台契约恰好等同的空闲引擎（`legvar` = legacy+预拉伸，
`offvar` = official+保比例）以**记录在案的**同一提示词 + 同一张脸图 + seed 42 补跑，
六条全部可比。旧的 a6/a7 产物保留在盘上，但不进对照表。

**判据补充** 一次实验的产物，必须和**生成它的完整请求**一起落盘。
产物本身不是证据 —— 没有请求体的 mp4 只能证明"跑过一次"，不能参与任何对比。
另：`a7` 那次日志与 mp4 甚至不是同一次运行 —— 最后一次提交因 JSON 多一个 `}` 而 400
失败并把日志截断重写，mp4 来自更早一次成功的提交。**日志与产物必须能互相锚定。**

### P-M0 根因:测量值是匿名的（五次同类错误的总账）

同一类错误在本任务中出现了**五次**。它们表面各异，根因只有一个：
**我取到的每个测量值都不带身份，读取方也从不校验身份。**

| # | 现象 | 匿名在哪里 |
|---|---|---|
| 1 | `docker logs --since` 时区错位，读到别的请求的 rows | rows 行不含 request id |
| 2 | probe 脚本不等终态就退出，读到上一发的 rows | 同上 |
| 3 | 空目录被 `ls && echo done` 判成成功 | 存在性 ≠ 内容 |
| 4 | 两侧 dump 点不一致（广播后 vs 转换前、merger 前 vs 后） | dump 文件不含来源标注 |
| 5 | 旧容器占着端口，readiness 探到的是 19 小时前的 FL2VA 引擎 | 探针只验"有响应"，不验"是谁" |

"下次更小心"不是修复。修复是让匿名值不可能被使用：

**四道闸门（已实现于 `serve.sh` / `req.sh`）**

1. **引擎发布身份**：就绪后写 `<tag>.identity`，含 served_model / requested_model /
   容器 id / 端口 / 主机 / 解析后的契约。
2. **提交前验身份**：`req.sh` 比对端口上活着的模型与 identity 文件，不一致直接
   `INVALID` 退出，绝不发请求。
3. **端口占用即拒启**：`serve.sh` 发现端口已有 MiniMax 响应就拒绝启动并列出容器名
   —— 只防同名容器不够，别的名字一样能占端口。
4. **行数校验证明来源**：引擎每步每 rank 打一行 rows。新增行数不是步数的整数倍，
   说明有并发请求在写，`ROWS` 记为 `INVALID` 而不是给一个看着合理的数。

另外 RESULT 行现在自带契约名，请求体逐字进日志 —— 一段日志摘录必须自解释，
不能依赖读的人记得当时的上下文。

**第 6 次，新变种：被读取的"东西"是脚本自己**

现象：一次请求提交失败，`JSON decode error ... Extra data`，日志里的请求体末尾多一个 `}`。
本地用同一份脚本复现，JSON 完全合法。

根因：我在那次运行**进行中**用 `cat > req.sh` 覆盖了脚本。`cat >` 是原地截断写入
（同一 inode），而 bash 是边执行边读脚本的 —— 文件在读到一半时被改写，后续读取偏移
错位，于是执行出了本不存在的内容。

修复：改用**原子替换** —— 先写 `.req.sh.new` 再 `mv -f` 覆盖。`mv` 只改目录项，
正在运行的进程继续持有旧 inode，互不影响。

这仍属同一族（用一个东西之前不验证它的身份与稳定性），只是这次不稳定的是脚本本身。
**推论**：凡是可能被并发读取的产物（脚本、fixture、identity 文件），一律原子替换，
不得原地截断。

**仍未根治的一处**：`_log_step_memory` 打印的行本身没有 request id。上面第 4 条是
在没有 id 的前提下能做到的最强校验（能检出并发，不能定位归属）。真正的根治是在引擎
日志里加 request id，见下条产品建议。

### P-M7 用 n=1 给随机量归因（我自己下过的一条错误结论，已撤回）

前面几条防的是"测量值属于谁"。这条是另一族：**测量值属于谁是对的，但它是个随机变量，
而我拿单次抽样当成了系统性差异。**

我曾据 seed 42 的一轮对照下过结论：*official 契约会让人物变成披肩长发、不忠于参考图，
legacy 契约则保持参考图的扎发* —— 六臂里 official RNG 的两臂长发、legacy RNG 的四臂扎发，
看起来完美分离。

**这条结论是错的。** 换 seed 43 复测立刻反号：legacy 出披发、official 出扎发。
随后固定几何、只在噪声两轴上做 2×2，跨 5 颗种子共 20 条样本：

| 臂 | rng_mode | 条件噪声形状 | seed42 | 43 | 44 | 45 | 46 | 扎/披 |
|---|---|---|---|---|---|---|---|---|
| dCTRL | legacy | legacy_oversized_slice | 扎 | 披 | 披 | 扎 | 披 | 2/3 |
| dCND | legacy | condition_shape | 扎 | 披 | 披 | 扎 | 披 | 2/3 |
| dRNG | official | legacy_oversized_slice | 扎 | 扎 | 披 | 扎 | 披 | 3/2 |
| dBOTH | official | condition_shape | 扎 | 扎 | 披 | 扎 | 披 | 3/2 |

20 条里扎发 10 / 披发 10，**每一臂自己都同时产出两种发型**。legacy RNG 4/6、
official RNG 6/4，n=10 对 n=10，差一个样本，远不构成差异。
四臂 16 个产物两两 md5 与体积均不同，说明两个旋钮都确实改了输出 —— 只是改的是
**抽哪一张签**，不是改分布。

值得单记的一点：**dCTRL 与 dCND 逐种子发型全同，dRNG 与 dBOTH 逐种子发型全同。**
发型只随 `rng_mode` + seed 走，`visual_condition_noise_shape_mode` 在这条链路上
不改变身份层面的结果。

**根因**：发型是采样级彩票。参考图是一张超宽幅面部特写（1664×656），头发大部分在画外，
模型必须自己补全 —— 这类被裁掉的属性本来就由噪声决定。而"换 RNG"在效果上等价于
"换一颗种子"，于是 n=1 的对照必然把一次抽签读成一个效应。

**判据**：随机量的归因，样本量必须先于结论。一个契约轴要被判为"降低身份保真"，
最低标准是同轴多种子的**比率差**，不是一次并排。凡是模型需要自行补全的属性
（画外的头发、服装、背景），默认按随机量处理。

真正系统性、可复现的只有**拉伸**一条：legvar 在 seed 42 和 43 两次都横压，
其余所有臂两颗种子都不压，与 `legacy_canvas_prestretch` 100% 绑定，与噪声无关。
详见 P-C1。

判定素材（3s/480p，rows 全为 19278，几何恒定）：
`/nfs-output/h3_align01/{dCTRL,dCND,dRNG,dBOTH}/d2-seed{43,44,45,46}.mp4`

### P-M1/2/3 的共同根因与产品建议

三次都是**用一条共享的、按时间排序的日志流去归因单个请求**，而
`denoise_loop.py:_log_step_memory` 打印的行里**没有 request/task id**：

```
H3 denoise step 1: rows video=115024 audio=1206 | driver free ... | torch allocated ...
```

只要日志里带上 task id，这三类错误一个都不会发生。**建议在 `_log_step_memory`
增加 request 标识**（forward context 里已有 step idx，加 id 是同量级改动）。
这不属于对齐任务范围，但属于同一批代码的可观测性缺口，单独提。

## 二、契约/代码问题

### P-C1（P0）参考图被上游拉伸到出片画布

**现象** 任意源比例的参考图，进 packed sequence 后行数恒为 7168。

**证据**（`req.sh`，每张图行数 = n=2 与 n=1 的 rows 差）

| 源图 | 比例 | 带 width/height | 不带 width/height |
|---|---|---|---|
| 1344×768 | 1.75 | 7168 | 7168 |
| 2560×1024 | 2.50 | 7168 | **10240** |
| 3072×1024 | 3.00 | 7168（被接受） | **拒绝** |

拒绝信息 `reference image aspect ratio must be in [0.4, 2.5], got 3072x1024`，
抛出点 `pipeline_minimax_h3.py:537`。

**根因** `vllm_omni/entrypoints/openai/serving_video.py:157-164`：只要 `vp.width`
与 `vp.height` 同时存在，就把每张参考图 LANCZOS **拉伸**到出片画布。

**影响**
1. 违反官方语义 —— 官方 `MiniMaxH3ImageReference` 明确 "It never binds the
   generated geometry"；
2. 是**拉伸**不是裁剪，参考图宽高比被破坏，直接损伤参考保真度；
3. 让 `_reference_image_shape` 的 `[0.4, 2.5]` 校验在生产路径上形同虚设；
4. 面积封顶要防的 10240 rows/图 只在不传 width/height 时才可能出现。

**处置** 修复点在**服务层**，且该段是所有视频模型共用的通用代码，必须按模型能力
开关，不能一刀切。需要在 strategy 里增加 `reference_image_geometry_mode`。

**人工验收结果（2026-08-17）：可见缺陷已确认**

素材：Z-Image 生成的 1664×656（比例 2.537）正面人脸，prompt 为明亮正面特写。

| | 参考图进模型时的几何 | rows | 峰值 | wall |
|---|---|---|---|---|
| official | 5184×2048，保留 2.537 | 118224 | 35919 MiB | 1101s |
| legacy | 3584×2048，**横向压缩约 30%** | 115024 | 35379 MiB | 1023s |

用户对照参考原图判定：**legacy 版本的人物相对原图明显被拉伸**。

因此这不只是契约不符，而是**现网正在发生的画质缺陷**：facade 恒传 width/height，
预拉伸恒触发，所以任何宽高比不等于出片画布的参考图都会被压扁后再送进模型。
16:9 出片 + 竖图或宽幅参考图是常见组合。

**注意先前的反例不成立** 更早用街景素材（背影、暗光）的一组看不出差别，那是素材
问题不是结论：背影 + 暗光下 30% 横向压缩不可观测。正面特写才是可判据的场景。
教训：人工验收的素材必须针对被验证的具体假设来选，不能用"看起来像典型请求"的素材。

**成本（2026-08-17 实测五臂，同一素材 face1.png 1664×656、同 prompt、seed 42）**

先前写的 "+3200 rows / +7% 耗时" 只对**短边保持 2048** 的那一档成立。把短边一并
下调后，结论反转：

| 臂 | 参考图进模型 | rows/图 | 总 rows | wall | 峰值 | 比例 |
|---|---|---|---|---|---|---|
| abLEG（现网） | 3584×2048 | 7168 | 115024 | 1023s | 35379 MiB | ❌ 横压 30% |
| geoonly（保比例 @2048） | 5184×2048 | 10368 | 118224 | 1220s | 35913 MiB | ✅ |
| **se1024（保比例 @1024）** | 2592×1024 | **2592** | **110448** | **1050s** | 36173 MiB | ✅ |

（目标序列 107856，rows/图 = 总 rows − 107856。）

**保住原始比例不需要用资源去换。** se1024 比现网少 4576 rows（−4%），耗时持平，
而比例是对的。现网那 7168 rows/图 里有相当一部分，是花在把人脸横向压扁上的。

因此产品结论应表述为：**"忠于原图比例"与"省资源"不是权衡关系**，需要权衡的只是
参考图的清晰度（短边取值）。短边旋钮已提升为正式生产旋钮，见
`test_short_edge_is_a_production_knob_when_the_aspect_ratio_is_preserved`。

### P-C1b（P0，新）准入范围绑在契约名上，去掉预拉伸后会硬拒真实用户图

**发现方式** 隔离矩阵的 `geoonly` 臂（legacy 契约 + `official_short_edge` 几何）
提交 a6 素材直接 400：

```
reference image aspect ratio must be in [0.4, 2.5], got 1664x656
```

同一张图在**全 legacy** 臂（abLEG）是能跑完的。

**根因** `reference_image_aspect_ratio_range` 挂在契约预设上（legacy `[0.4, 2.5]`，
official `[0.25, 4.0]`），但它约束的对象取决于**几何模式**：

- legacy 预拉伸：校验器看到的是已被改写成出片比例的画布 → 1664×656（2.54）
  以 1344×768（1.75）的身份通过校验，`[0.4, 2.5]` 从不会被真正触发；
- 不预拉伸：校验器看到的是**原图** → 2.54 超出 2.5，硬拒。

即 legacy 的 `[0.4, 2.5]` 之所以成立，正是靠预拉伸把超范围比例掩盖掉。这与 P-C1
"让 `[0.4, 2.5]` 校验形同虚设" 是同一件事的两面：一旦按用户要求"忠于原图比例"，
这条形同虚设的校验会立刻变成**真实的拒绝**。

**影响** 若只发几何修复而不同时放宽准入范围，比例落在 (2.5, 4.0] 与 [0.25, 0.4)
的参考图会从"被静默压扁但出片"变成"直接 400"。对用户而言这是**回归**。

**处置** 准入范围跟随**几何模式**而非契约名：几何为 `official_short_edge` 时，
范围一并取 official 的 `[0.25, 4.0]`。落点
`strategy.py:resolve_strategy`，用例
`test_dropping_the_prestretch_widens_the_admission_envelope`。

该范围**只做准入判断**，不参与任何已放行请求的处理，所以放宽它不会改变任何原本
就能跑通的结果 —— 隔离实验的可归因性不受影响。

**教训** 一个"从未触发过的校验"不等于"可以随便改的校验"。它没触发是因为上游有别
的行为在掩盖它；移除那个行为的同时必须重新评估它。

### P-C4（P0，新）prompt_embeds 的 vision 行与官方实质不同

**现象** 同一请求、同一权重、token 与 tags 逐个一致，但条件 hidden state 的
vision 行与官方相差极大；text 行几乎完全一致。

**证据** `tools/minimax_h3_parity/analyze_embeds.py`，全量 1813×5120 逐元素：

| | 行数 | cosine | max_abs | mean_abs | 完全相等占比 |
|---|---|---|---|---|---|
| text 行 | 19 | **0.9999992** | 64 | 0.034 | 10.6% |
| vision 行 | 1794 | **0.8760** | **18641** | 0.259 | 2.7% |

张量整体 std 仅 14.4，而 vision 行 max_abs 达 18641；1 个 bf16 ULP 在该量级是
0.06，差五个数量级。`row_max_abs.median = 2.0`，`rows_above_10x_median = 35`，
最差行 36 / 128 / 143 / 45 / 209 全部落在 vision block 内。

两侧各自 bit 确定（见 P-A2），所以这不是噪声。

**已排除** token ids 一致、token tags 一致、参考图归一化几何一致（两侧均
1792×1024，短边 1024，LANCZOS）。差异发生在"像素进 processor 之后、hidden
state 出来之前"。

**待查方向**（按可能性）

1. `mm_token_type_ids` / 分模态 rotary 布局 —— 官方
   `get_qwen3vl_prompt_embeds` 用 `processor.create_mm_token_type_ids` 驱动
   Qwen3-VL 的按模态 rotary。若 vLLM 侧构造方式不同，影响**只**落在 vision 行，
   且与 "token id 一致" 并不矛盾（id 相同、位置编码不同）。这与观测形态最吻合。
2. `image_processor` 预处理参数（归一化均值/方差、rescale、patch 切分）。
3. vision tower 的 dtype 或 TP 切分方式。

**为什么之前没暴露** exact 阶段（geometry/packing/rng）全绿，token 全一致，
32 点 head/tail 采样只看到 1 ULP 量级。只有全量逐元素 + 按模态拆分才看得见。
这正是文档 §7.2「不要只比较最终产物，必须比较上游阶段」要防的情形。

**定位结果（逐环节实测，非推测）**

| 环节 | 比较对象 | 结果 |
|---|---|---|
| 图像预处理 | `pixel_values` / `image_grid_thw`（processor 原始输出） | **逐字节一致** |
| rotary 索引 | `_get_rope_index` vs transformers 5.14 `get_rope_index` | 逐行一致 |
| 模态标记 | `mm_token_type_ids`（`image_token_ids=[151655]`） | 一致 |
| vision tower | `image_embeds` [1792, 5120] bf16 | cosine **0.9985**，mean_abs 0.041 |
| 50 层解码之后 | `prompt_embeds` vision 行 | cosine **0.8760** |

vision tower **未参与 TP**（其模块只接受 `config`，不接受进程组），两侧都是复制的整塔。

**当前判断** 链条上没有发现实现错误。塔的 0.15% 偏差（bf16 下重写实现的正常量级）
经 50 层解码器放大为 12%，且 vision 行每层都被 deepstack 特征再次注入，放大路径合理。

**仍不能下的结论** 「0.15% 属于正常」需要与同一实现内部的 bf16 抖动比较才成立，
而那正是 P-A3 中测不出来的基线。故只能表述为「量级合理」，不能表述为「符合预期」。

**方法论代价（值得记）** 定位过程中在采样点上连错四次：空目录当成功、纯文本比
ref2va、dump 落在广播之后、hook 落在 patch merger 之前。四次都是「两侧测的不是同一个量」。
根因是**猜**测量点而不是**定义**测量点；最后改用 transformers 公开 API
`get_image_features()`（语义明确为「要 scatter 进 inputs_embeds 的那份」）后一次成功。
结论：对拍点必须锚定在双方都有明确定义的接口边界上，不能锚定在内部模块输出上。

### P-C5（已验证通过）checkpoint 转换无损 —— §5.9 第一项

**背景** 官方仓库把同一个 DiT 存了两套布局：根级 diffusers 命名 638 张量（q/k/v 分开），
分区命名 535 张量（qkv 融合）。vLLM-Omni 读分区并在装载时做 grouped-QKV / fused-MLP
转换，而**此前所有对拍都发生在这段转换之后** —— 转换本身从未被检验过。

**做法** 不建模型，直接比两份 checkpoint 的字节（`tools/minimax_h3_parity/verify_checkpoint_conversion.py`）。
两边同 dtype、都未做过算术，所以**逐位相同**是正确的判据，任何差异都是布局差异。
关键设计：融合张量的顺序是**测出来的**，不是假定的 —— 脚本枚举候选顺序逐位比对，
并报告**是哪一种**匹配。

**结果（2026-08-17，Ref2VA 分区 vs 根级 transformer_ref）**

```
verdict: checkpoints agree
  430  同名张量逐位相同
   52  qkv 组 → 全部 grouped_per_head（逐头交错，非简单 concat）
   52  SwiGLU fc1 → 全部 up_gate（up 在前、gate 在后）
    0  未映射 / 未重建
  分区侧独有：rope.inv_freq（推导缓冲，非学习权重）
```

430 + 52×3 + 52 = 638，账目闭合。

**为什么值得单独测** qkv 的头序、SwiGLU 的两半顺序，接反之后模型**照样能跑、照样出
合理视频**。这类缺陷不会报错，只会表现为"质量好像差一点"，而事后的画质对比无法把它
与采样差异区分开。必须在权重层面判定。

**顺带确认的映射**（脚本按名字提假设、用逐位比对证伪）：

## 五、容量问题

### P-R1 BF16 相对 INT8 的包络收缩

数据见 `H3-对齐-机器分配表.md`。要点：

- BF16 与 INT8 的差是 **4.5 GiB/卡**（DiT 15.5 vs 11.0）；INT8 只省 18G/29%，
  且 text_encoder 与 VAE 两边是同一批文件（软链接）。
- t2va / fl2va 在 768p/15s 余量充足（34–36 GiB），**不受影响**。
- ref2va 门槛约 **165k rows**：≤165k 稳过、≥172k 必挂。
- 需要对外限制的是 ref2va 的参考素材总量，不是分辨率或时长本身。
