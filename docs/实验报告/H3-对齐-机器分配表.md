## 已得结论

### 权重体积（问题 4）

| | 总计 | transformer | text_encoder | vae |
|---|---|---|---|---|
| BF16 `MiniMax-H3/Ref2VA` | 135G | 62G | 63G | 9.8G |
| INT8 `MiniMax-H3-Ref2VA-INT8` | 44G | 44G | → 软链 BF16 | → 软链 BF16 |

INT8 只省 18G（29%），且仅 DiT；text_encoder/VAE 两边是同一批文件。
`ignored_layers` 保留了全部 `adaln_proj.linear` 与 `audio_patch_proj`，故达不到 50%。
折算到卡：BF16 15.5G/卡 vs INT8 11G/卡，**差 4.5G/卡**。

**能。** 430s 就绪，稳态 24173 MiB/卡（4×A100-40G，TP4 + cpu-offload）。

### 参考图几何（交接的未决问题）—— 已定论

用"同条件下 n=1 与 n=2 的 rows 差"测每张参考图的行数（该差值与画布无关）：

| 源图 | 比例 | 带 width/height | 不带 width/height |
|---|---|---|---|
| img 1344×768 | 1.75 | 7168 | 7168 |
| wide 2560×1024 | 2.50 | 7168 | **10240** |
| ratio3 3072×1024 | 3.00 | 7168（**被接受**） | **6 秒内拒绝** |

拒绝信息：`reference image aspect ratio must be in [0.4, 2.5], got 3072x1024`，
抛出点 `pipeline_minimax_h3.py:537 _reference_image_shape`。

**归一那一跳 = `vllm_omni/entrypoints/openai/serving_video.py:157-164`**：

```python
if input_image is not None and vp.width is not None and vp.height is not None:
    target_size = (vp.width, vp.height)
    resized_images = [image.resize(target_size, Image.Resampling.LANCZOS) ...]
```

只在 width/height 同时存在时触发，与实测两条分支完全吻合。后果：

1. 生产路径（facade 恒传 width/height）下，参考图被**拉伸**（非裁剪）到出片画布，
   丢掉自身宽高比，再由短边 2048 归一 → rows/图 恒 7168。这与官方语义直接冲突：
   官方 `MiniMaxH3ImageReference` 明确 "It never binds the generated geometry"。
2. 同一条路径让 `_reference_image_shape` 的 `[0.4, 2.5]` 校验**形同虚设** ——
   任何比例的图到达时都已是画布比例。
3. 面积封顶要防的 10240 rows/图 只在**不带 width/height** 时才会出现。

## 采集陷阱（两次都踩到，已修）

`docker logs --since` 传入不带时区后缀的时间戳时，docker 按**本地时区**解释。
UTC+8 主机上传 UTC 戳等于把窗口前移 8 小时，`head -1` 于是返回更早请求的 rows。
旧 harness 用 `tail -1` + 共享容器，本 harness 初版用 `--since` + `head -1`，两者都会
把不同用例读成同一个数。现改为：提交前统计已有匹配条数 `PRE`，取第 `PRE+1` 条。

旧 `runcap.sh` 另有两处：硬编码 `VLLM_OMNI_H3_REF_IMAGE_SHORT_EDGE=768`（而镜像里
根本没有读这个 env 的代码），以及两次调用相隔 1 秒、`docker run --name h3e` 互相
`rm -f` 争抢同一容器。
