# E0/E1 执行结果：烘焙损失量化 + 同引擎换权重（2026-10-25 夜）

> 结论先行：**候选 B（烘焙丢增量）与候选 A（v1.3 本身弱）同时成立**。
> E0 量出 0.0625 这条线只剩约 36–42% 的增量模长、方向余弦仅 0.27–0.32；
> E1 像素级验证显示 **v1.1（缩放 1.0）全程干净，v1.2 短片可用但 15s 尾部崩，v1.3 从短片就崩**。
> E2（运行时 LoRA）被两道闸拦住，未取得数据，停在需决策处。

## E0：烘焙保留比（纯 CPU，fp32，逐层）

复刻 `bake_turbo_lora.py` 的映射（qkv per-head 交错、SwiGLU 半序交换），
每 25 个融合张量抽 1 层，共 9 层可测。`retention = ||ΔW_baked|| / ||ΔW_ideal||`，
`cosine = cos(ΔW_baked, ΔW_ideal)`。

| 变体 | 缩放 | retention 中位 | cosine 中位 | retention 区间 |
| --- | ---: | ---: | ---: | --- |
| turbo4 **v1.1** | 1.0 | **1.012** | **0.887** | 0.864 – 1.031 |
| turbo4 **v1.2** | 0.0625 | **0.359** | **0.270** | 0.177 – 0.793 |
| turbo4 **v1.3** | 0.0625 | **0.423** | **0.319** | 0.337 – 0.823 |
| turbo8 v1.1 | 0.0625 | 0.400 | 0.301 | 0.278 – 0.743 |

逐层样本（节选）：

| 变体 | 张量 | retention | cosine | 改变值占比 |
| --- | --- | ---: | ---: | ---: |
| v1.1 | `blocks.14.attn.qkv_proj` | 1.031 | 0.997 | 50.0% |
| v1.1 | `blocks.2.mlp.fc1` | 1.030 | 0.927 | 42.3% |
| v1.1 | `blocks.25.mlp.fc2` | 0.864 | 0.680 | 24.8% |
| v1.2 | `blocks.0.attn.out_proj` | 0.470 | 0.355 | 3.4% |
| v1.2 | `blocks.25.mlp.fc2` | 0.177 | 0.133 | 0.9% |
| v1.3 | `blocks.0.attn.out_proj` | 0.570 | 0.432 | 6.9% |
| v1.3 | `blocks.31.attn.out_proj` | 0.337 | 0.253 | 2.0% |

判读：

- **缩放 1.0 的 v1.1 基本无损**（retention≈1，qkv 余弦 0.997），个别层（fc2/out_proj）余弦 0.68–0.70，
  说明即使放大 16 倍，增量相对权重仍偏小、会被 BF16 尾部吃掉一部分。
- **缩放 0.0625 的三档掉得很厉害**：只剩 36–42% 模长，方向余弦 0.27–0.32。
  即"留下来的那部分"主要是基座权重的 BF16 量化残差，不是增量本身。
- 与组装元数据里"改变值占比 3.4%–4.6%"完全对得上，互相印证。
- `max_abs_error=0` 只证明"烘焙结果 == 本次有损舍入"，不证明增量被保住。

### 与 E0 的关系

- v1.1 保留增量 → 全场景干净。
- v1.2 与 v1.3 保留比接近（0.359 vs 0.423），但质量差一档：
  v1.2 短片可用、长片尾部崩；v1.3 从短片就崩。
  **所以烘焙损失是共同底色（B），v1.3 另有自身弱点（A）**，两者叠加而非互斥。
- 这解释了为什么"v1.2 出片更接近基座"曾被解释成"增量本来就小"——实际主要是舍入损失，
  但 v1.2 的损失尚未越过可用阈值。

## E2：运行时 LoRA（未取得数据，两道闸）

按你的计划用基座 `MiniMax-H3/FL2VA` + v1.3 LoRA，实测撞了两道闸：

1. **`--lora-backend distill` 不被 H3 支持**
   `Pipeline MiniMaxH3Pipeline does not support loading distilled LoRA weights.`（四个 rank 全拒）
   该后端走初始化期 `load_lora_weights` 融合；H3 的 Turbo 适配器是**请求级动态 LoRA**，
   入口在 `pipeline_minimax_h3._load_diffusion_lora_adapter` → `load_minimax_h3_turbo_lora`。
2. **改用请求级 `lora` 字段后**：`RuntimeError: MiniMax-H3 Turbo dynamic LoRA does not support
   model-level CPU offload`。因为启动带了 `--enable-cpu-offload`（文档 CLI 参数里有它）。

**需要你定的两个点**（我没自行改）：

- 是否允许 E2 关掉 `--enable-cpu-offload` 重跑？风险：基座 BF16 13 分片常驻显存，
  15s 用例可能 OOM，只能先跑 5s。
- 顺带确认：E2 的 `lora_scale` 要 1.0 与 2.0 两档，2.0 一档要不要也跑 15s（内存风险更高）。

另：**sigma 先决条件已核对通过**——`shifted_sigmas(6)` 代入 4 步 base_schedule 得
video `[1, 0.947, 0.857, 0.667, 0]`、audio `[1, 0.9, 0.75, 0.5, 0]`，与你给的完全一致；
且这两组蒸馏网格本身就是均匀网格，所以运行时路径（均匀 4 步再平移）与烘焙版 sigma 相同，E2 可比。
你对旧文档"C 组带不上蒸馏调度"的质疑成立。

## E-A：提高强度能不能救 v1.3（2026-10-26 执行）

### 做法

用 `bake_turbo_lora.py --scale` 把 v1.3 重烘到 **0.25（4× 名义）** 与 **0.5（8× 名义）**，
其余完全不变（同基座、同 yaml、同 4 步、seed 42），与已有的 0.0625 及 v1.1 做四行盲评。

- 烘焙：`s025` 13 分钟、`s05` 12 分钟，各 62 GB。
- 模拟保真度（E0c）：0.25 → retention 0.767 / cos 0.602；0.5 → 0.935 / 0.776。
  即这两个点同时也是"更少烘焙损失 + 更强增量"，两个变量同时变，判读时要注意。

### 踩到的工具缺陷（已修）

`--partition-out` 生成的 `model_index.json` **从基座继承元数据**：`sigma_shift_scales` 变成
`12.0/3.0`、`base_schedule` 丢失。直接起服务会用错调度。已按源 v1.3 的 `_minimax_h3`
把 `shift=6/3`、5 点调度补回，并把 `effective_lora_scale` 改成对应的 0.25 / 0.5。

### 盲评结果（seed 42）

`neon_night`（A=0.5 / B=0.0625 / C=0.25 / D=v1.1）：

| 行 | 强度 | 判读 |
| --- | ---: | --- |
| A | 0.5 | **彻底崩**：彩色噪点马赛克，无任何结构 |
| B | 0.0625 | 竖条纹，无街景 |
| C | 0.25 | **结构回来了**（摊位/行人可辨），但**过曝、过饱和、招牌颜色被拉爆** |
| D | v1.1 | 干净自然 |

`sports`（A=v1.1 / B=0.0625 / C=0.25 / D=0.5）：

| 行 | 强度 | 判读 |
| --- | ---: | --- |
| A | v1.1 | 干净 |
| B | 0.0625 | 地板糊成橙色斑块 |
| C | 0.25 | **比 B 更碎**：观众席与地板碎成像素碎片 |
| D | 0.5 | 彩色噪点马赛克 |

### 结论

- **强度不是单调的质量轴**：霓虹上 0.25 把结构找回来了，运动上 0.25 反而更碎；0.5 两个场景都崩成噪声。
  调强度只是在**更换失败形态**，没有收敛到可用。
- 因此 **v1.3 在 4 步下无法靠强度调参救回**，与上游"2.0 更稳但仍不好"一致。
- 仍然唯一干净的是 **v1.1（1.0）**。
- 唯一没触达的格子是"2× 且烘焙零损失"（运行时 0.125），即 E2；按现有证据预期仍不可用。

## 附：`--partition-out` 元数据缺陷的修复（2026-10-26）

### 缺陷

`assemble_partition` 把 base 分区里的**所有**文件软链到新分区，包括 `model_index.json`：

1. 出包分区读到的是**基座**契约（`shift 12.0`、无 `base_schedule`），蒸馏权重需要的 `shift 6` 被静默丢弃；
2. 软链意味着后续任何元数据修改都会**穿透写回基座**（本次手工补 s025/s05 时已经发生过一次，
   已按同族参考还原）。

### 修复（`tools/minimax_h3/bake_turbo_lora.py`）

- 新增 `--contract-from <model_index.json>`：显式指定蒸馏契约来源。
- 无显式契约时，只有当基座本身是蒸馏版（含 `distilled`/`base_schedule`）才继承，否则**拒绝出包**。
- `model_index.json` 一律写真实文件；目标处已有软链先 `unlink`，避免穿透。
- 组件默认**实体拷贝**（自包含），`--symlink-components` 可退回软链省空间。
- 自动写入 `effective_lora_scale` 并打印所用契约。

回归测试：`tests/tools/minimax_h3/test_bake_turbo_lora_partition.py`，6 例（含"已有软链不得穿透"）。

## E2-补：运行时 LoRA（零烘焙损失 + 名义强度），2026-10-26

这是之前唯一没触达的格子。做法：基座 `MiniMax-H3/FL2VA` + 请求级 `lora`
（`minimax_h3_fl2v_turbo_4step_v1.3_768p_bf16`，scale 1.0 / 2.0）+ `extra_params{flow_shift:6, audio_flow_shift:3}`，
`--enable-cpu-offload` 关闭、只开 `VLLM_OMNI_H3_OFFLOAD_COMPONENTS=1`（单卡 29.5 GB，余量 11 GB）。

> 确定性已验：同一条无 LoRA 用例连跑两次 sha256 完全相同（`bf53f189…`），
> 带 LoRA 的输出为 `b5dac1c2…`，因此差异确实来自适配器，不是跑间抖动。

### 盲评（seed 42，四行）

`neon_night`（A=rt2.0 / B=烘焙0.0625 / C=rt1.0 / D=v1.1）：

| 行 | 配置 | 判读 |
| --- | --- | --- |
| A | 运行时 2.0 | 结构在，但颗粒/过曝明显 |
| B | 烘焙 0.0625 | 竖条纹崩坏 |
| C | **运行时 1.0** | **不崩了**：正常夜市街景，结构完整，偏软、噪点略多 |
| D | v1.1 锚点 | 最干净 |

`sports`（A=v1.1 / B=烘焙 / C=rt1.0 / D=rt2.0）：同样——
烘焙崩（橙色斑块）、**运行时 1.0 结构正常（偏软）**、运行时 2.0 碎裂、v1.1 干净。

### 结论更正

**此前"v1.3 崩与我们的烘焙无关"的判断是错的。** 错的根源是我把"强度"和"保真度"混在了一起：

- 我之前用 0.25 / 0.5 强度去论证"保真度接近 1.0 时仍崩"，但那两档同时把强度放大了 4×/8×，
  崩是**过强**造成，不能用来否证烘焙损失。
- 补上"名义强度 + 零损失"这一格后：**崩坏消失，画面变回可用的街景/球场**。

所以归因修正为：

| 因素 | 角色 |
| --- | --- |
| BF16 烘焙（0.0625 线） | **主因**：把 v1.3 从"偏软"推到"崩坏" |
| v1.3 权重自身 | **次要**：零损失下仍比 v1.1 软、噪点更多，但可用 |
| 强度放大（2×以上） | 在 H3 上会过曝/碎裂，**不是修复手段**（与上游"2.0 更稳"不一致） |

落地含义：**v1.3 要用就必须走运行时注入，不能烘**；但即便如此仍不如 v1.1，
所以不改变"暂不上 turbo、等上游"的决定。

## E2-补二：运行时 v1.1 vs v1.3 的耗时与资源（2026-10-26）

一个实例只挂一个适配器（同实例内换适配器会把 worker 搞挂，见下）。基座 `MiniMax-H3/FL2VA`
+ 请求级 LoRA，`flow_shift=6/3`，4 步，关闭模型级 offload、只开 `VLLM_OMNI_H3_OFFLOAD_COMPONENTS=1`。

### 结果

| 路径 | 5s 墙钟 | 15s 墙钟（热态） | 峰值 GPU/卡 | 峰值宿主内存 |
| --- | ---: | ---: | ---: | ---: |
| **v1.1 烘焙**（scale 1.0，无损） | 58–60 s | **223 s** | 19.7 / 25.9 GB | 185.7 GiB |
| **v1.3 运行时**（scale 1.0） | **61 s** | **258 s**（首条 328 s 含编译） | **30.9 GB** | 133.0 GiB |
| v1.1 运行时（scale 1.0） | **不可用** | — | — | — |

- 运行时 v1.3 的 4 条 5s：61 / 61 / 64 / 77 s，比烘焙 v1.1 慢约 **3%**。
- 15s 热态 **258 s vs 223 s，慢 16%**。
- **显存贵 11 GB**：动态 LoRA 禁止模型级 offload，基座必须常驻 GPU（30.9 GB vs 19.7 GB）。
  代价换来的是宿主内存少 53 GiB（权重在卡上而不是 CPU 暂存）。

### v1.1 运行时跑不起来

预热请求 `RPC call to execute_model timed out`（630 s），随后引擎进入 `OmniEngineDeadError`
（`Stage-0 has no live replica`），后续请求 2–3 s 内全失败。同配置下 v1.3 的 6 条全部成功。
所以 **"运行时 v1.1 vs v1.3" 无法直接对比**，只能比"各自的可行路径"。

同实例内**换适配器**（v1.3 → v1.1）也会触发同样的 worker 挂死；一实例一适配器才稳定。

### 画面

- **5s**（neon / sports，seed 42 与 43）：v1.3 运行时**不再崩坏**，与 v1.1 烘焙同一水平

### 结论

- 烘焙损失是 **5s 崩坏**的主因，换运行时即可消除；但 **15s 的重影是另一回事**，
  运行时也压不住 → 这段更可能是 v1.3 权重在长序列上的固有弱点。
- 上 v1.3 的可行形态只有运行时，且要接受：**+16% 长片耗时、+11 GB 显存、15s 仍重影**。
- v1.1 走烘焙仍是最优：无损、快、15s 干净。
