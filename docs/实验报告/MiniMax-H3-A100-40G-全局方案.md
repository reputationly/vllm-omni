## 0. 为什么要重写规划

到目前为止修掉的 6 个问题（#13 quant_state 不搬、#14 adaln 按 weight.dtype 截断、
#15 异步超时写死 30 秒、#16 宿主 OOM、"摘掉 `--enable-cpu-offload` 反而加载失败"、

## 1. 唯一的结构性约束

三条硬件/框架事实，其余全是它们的推论：

| 事实 | 后果 |
|---|---|
| **USP/Ulysses SP 在每个 rank 上复制整份 DiT 权重**（不是切分） | 显存需求 = 单卡装下整个模型，加 rank 数不减显存；宿主上也是每 rank 一份 CPU 主本 |
| **卡是 40 GB，A100 = sm_80** | 有 INT8 tensor core，**没有 FP8/FP4**。NF4 只省显存不提速（bnb `matmul_4bit` 先反量化回 bf16 再走普通 GEMM） |
| **`--enable-cpu-offload` 一个开关同时控三件事** | 见下节 |

### 1.1 一个开关控三件事

`--enable-cpu-offload` 实际耦合了三个本该独立的决策：

| 决策 | 由谁实现 | 现在的行为 |
|---|---|---|
| **A. 加载路径**：权重怎么进内存、在哪里量化 | `diffusion_model_runner.py:214` 的 `load_device = "cpu" if enable_cpu_offload ...` | 开 → 先落 CPU，再整模过一遍 GPU 做在线量化，再搬回 CPU |
| **B. 静态驻留**：空闲时权重在 GPU 还是 CPU | `ModelLevelOffloadBackend.enable()` | 开 → DiT 常驻 CPU |
| **C. 请求内搬运**：一次推理中谁进谁出 | `SequentialOffloadHook` | 开 → 编码器 ↔ DiT 互斥换页 |

于是"我只想要 C"变成了"必须一起接受 A 和 B"。
**"摘掉 `--enable-cpu-offload` 在加载期就崩"** 就是这个耦合：没有 A，
66 GB 的 bf16 DiT 会在量化前整个落到 40 GB 卡上。这个开关是**加载期承重**的，
不是运行期可选项。

## 2. 实测预算表

### 2.1 显存（0025，480p/20 步，NF4 DiT + bf16 编码器）

| 时刻 | `nvidia-smi` | 构成 |
|---|---|---|
| 加载完成（编码器驻卡，DiT 在 CPU） | **24419 MiB** | 编码器 ~16 GB + VAE/CUDA ctx/NCCL ~8 GB |

| 假想两者同驻 | **~47.5 GB** | 超出 40 GB 约 **7.5 GB** |

> 我此前算过"28.3 GB 装得下"，那是错的：漏了编码器的真实大小（16 GB，不是从
> 换页计数器读到的 12.8 GB——计数器只统计实际搬动的参数）和 ~8 GB 的 VAE+context。

> 加 `empty_cache()` 后读数一字节没变，就是因为压根没有可回收的东西。
>
> **结论：换页不是一个可以绕开的设计选择，是当前配置下被迫的。**

## 4. 目标架构

把 A/B/C 解耦，各自由独立的条件决定：

| 决策 | 目标状态 | 达成手段 |
|---|---|---|
| **A. 加载路径** | 直接以 NF4 落盘格式加载，bf16 **从不**出现在任何设备上 | 离线 NF4 checkpoint + 修 #5（离线 ckpt 被误判为 online） |
| **B. 静态驻留** | 编码器和 DiT 同时常驻 GPU | 编码器量化，把 16 GB → ~4.5 GB |
| **C. 请求内搬运** | 常态为**零换页**；只有确实放不下的档位才换页，且换页的 host 成本为零 | 已实现的常驻判定（判据改用真实预算）+ 换出不 copy |

达成后每卡预算：DiT-NF4 15.5 + 编码器-NF4 4.5 + VAE/ctx 8 + 激活 8 ≈ **36 GB / 40 GB**。

## 5. 执行顺序（按依赖排，不按疼痛排）

### P0 — 先让服务能连续服务（不改架构，最小改动）

**P0-1：换出时不 copy，只切指针** ← #16 的真解

现在 `SequentialOffloadHook._to_cpu` 的逻辑是：

```python
shadow = <pinned CPU 缓冲，首次分配后复用>
shadow.copy_(data)        # 每次换出 28 GB 的 D2H
owner.data = shadow
```

**权重在推理过程中是只读的，从来不会被修改。** 所以这个 copy 每次白搬 28 GB，
而且 shadow 必须是一块独立于"加载时 CPU 主本"的新内存——因为主本在首次换入后
失去了引用被释放了。净效果是把可回收的 anon 页换成了**永不归还的 pinned 页**。

改成：

```python
# 换入时记住 CPU 原张量
_cpu_home = owner.data
owner.data = _cpu_home.to(gpu)
# 换出时直接换回去，零 copy 零分配
owner.data = _cpu_home
```

| 指标 | 现在 | P0-1 后 |
|---|---|---|
| host `shmem` | 113–143 GB | **~0** |
| 每请求每 rank D2H | 28 GB | **0**（只剩换入的 H2D） |
| host 峰值 | ~250–300 GB | **~160 GB**（装得进 251 GB） |

风险：CPU 主本不是 pinned，H2D 不能真正 `non_blocking`。但**现在也没有**——
现在换入就是从 pageable 张量 `.to(device)`，所以没有回退。
另需同样处理 bnb `quant_state` 和 DTensor 两条分支。

**P0-2：验收** —— 连续 10 次 480p 请求不死，`shmem` 不再增长，逐次耗时无漂移。

### P1 — 消除换页（改架构）

**P1-0 之一：前端每请求泄漏 568 MiB（已完成，#28/#29/#30）**

> P1-0「宿主内存超账治理」拆成两块：这一块是**前端进程的泄漏**（已修完）；
> 另一块是 **worker 侧 ~198 GB 常驻压回预算**，见 #23，尚未做。

P0 把 host 峰值压到 ~160 GB 之后，剩下的抖动来自另一处：**API 前端进程每出一条
片子涨 ~568 MiB，永不归还**。0025 跑满 60 个请求后前端 `RssAnon` 到 46.4 GB。

机理三句话：

1. `tensor.numpy()` **不拷贝**，得到的 ndarray 借用的是 torch 那块内存。
2. torch 2.11.0+cu130 的 `libc10.so` **静态链了 mimalloc**。超过 ~512 KiB 的分配会拿到
   一个独占的 huge segment；从**非分配线程**释放这种 segment，只会把块挂到该页的
   deferred-free 链上，而这条链要等**拥有该页的线程下次从同页分配**才会排空——
   可这页只装了这一个分配，那次分配永远不会发生。
3. 后处理跑在引擎 busy-loop 线程上，最终释放 payload 的却是 API 线程。于是每一块
   借用缓冲**从来没被标记为 free**，任何 allocator 调参都收不回来。

0025 上的对照实验（`mech.py`，每轮一块 566 MiB）：

| 场景 | 每轮 RSS 增量 kB |
|---|---|
| torch 借用，同线程分配+释放 | 640 / **0 / 0** |
| torch 借用，别线程分配、主线程释放 | +584116 / −405016 / +409376（净涨且抖） |
| torch 借用，主线程分配、别线程释放 | +581644 / +581632 / +581632（**每轮必漏**） |
| numpy 自有内存，任意线程组合 | **0 / 0 / 0** |

第二行的抖动正解释了现场为什么不是干净的线性累积（0025 46.4 GB vs 0026 17.4 GB）。

修法分两层：

- **源头**（`pipeline_minimax_h3.py`）：后处理改成先 `np.empty` 拿 numpy 自有内存，
  再用 `torch.from_numpy(dst).copy_(src)` 灌进去。numpy（走 glibc）的内存跨线程释放
  永远正确。**顺带还更快**——`copy_` 把置换当分块转置做且多线程，而原来的
  `.clamp()` 在非连续张量上是单线程逐元素：后处理 5.3–11.7 s → **2.4–3.0 s**。
- **边界网**（`diffusion_engine.py` 的 `_reown_foreign_numpy`）：在 `postprocess_output`
  里把仍在借用外来内存的大 ndarray 换成自有内存，给树里另外 8 个同款泄漏点兜底
  （lance / audiox / stable_audio / omnivoice / soulx_singer×2 / dreamid_omni×2，AST 扫描
  11 处命中里的真阳性）。

| | r1(预热) | r2 | r3 | r4 |

> **一个走过的弯路，写下来免得重走**：网最初带一套"按父缓冲分组拷贝"的优化，前提是

**P1-1：文本编码器量化**

卡点已定位：`bitsandbytes_config.py:98` 的 `get_quant_method` 只在
`isinstance(layer, LinearBase)` 时返回量化方法。而 H3 编码器的四个线性层
（`MiniMaxH3Qwen3VLRowParallelLinear` / `MergedColumnParallelLinear` /
`QKVParallelLinear` / `VocabParallelEmbedding`，见
`vllm_omni/diffusion/models/minimax_h3/encoder.py`）是裸 `nn.Module` +
`nn.Parameter` + `F.linear`，**不是 vLLM `LinearBase` 子类**，量化器根本看不见它们。

这不是配置漏配，是模型移植时的结构缺口。修法是把这几个类接到
quant-method 感知的路径上。配置层已经通了——`ComponentQuantizationConfig`
支持按前缀路由（`{"transformer": nf4, "text_encoder": nf4}`）。

注意保持 `RowParallelLinear.forward` 里 **fp32 all-reduce** 的数值行为
（代码里有注释说明：bf16 all-reduce 会两次舍入并放大误差）。

收益：编码器 16 GB → ~4.5 GB/rank，两模型同驻成立，**C 整条换页路径在生产档不再触发**。

**P1-1 进展（2026-08-08，进行中）**

改法：把 `encoder.py` 里那四个裸 `nn.Module` 接到 `LinearBase` 路径上。这里有个
必须做的**解融合**——`qkv_proj` 拆成 `q_proj`/`k_proj`/`v_proj`，`gate_up_proj` 拆成
`gate_proj`/`up_proj`。原因是量化后 weight 是打包的 uint8，**没有"行"可以切**，
融合权重再按 TP 分片会切在包边界上。

*已坐实的收益*：

| 指标 | BF16 编码器 | NF4 编码器 |
|---|---|---|
| 空载显存 | 24419 MiB/卡 | **15675 MiB/卡** |
| 编码器换出量（`home-hit`/rank） | 12.82 GB | **4.31 GB** |

1. **量化算子本身没问题**——`bitsandbytes_config.py` 的 `BnBOnlineLinearMethod`

### P3 — 双机形态

0030 实测拓扑：**无 NVLink**；GPU0↔1、GPU2↔3 是 PHB（NUMA 0 / NUMA 2），
0/1 ↔ 2/3 跨 SYS；4 张 mlx5 @100 Gb/s 对所有 GPU 都是 SYS（无亲和，GDR 大概率降级）。

当前 `--usp 4` 横跨 SYS 边界。曾设想 **`--usp 2` × 2 副本**让每副本落在一个 NUMA 内、
吞吐翻倍。**实测否掉了（#26）**：

| 拓扑 | 单发 | 四发 makespan | 每 rank `anon-rss` |
|---|---|---|---|
| usp4 单副本 | 51.2–53.2 s | 208 s | **19 GB** |
| usp2 × 2 副本 | —（宿主 OOM） | — | **59.2 GB** |

机理：DiT 走 USP **复制**，每 rank 恒定一整份，切 usp 不改变它；而文本编码器的 TP
从 4 降到 2，每 rank 分片**翻倍**。rank 总数没变、总内存却更大，直接打爆宿主。

**结论：usp4 单副本是当前唯一可行拓扑。** 多副本的前提是先做 #19（编码器量化），
把每 rank 的编码器从 16 GB 压到 ~4.5 GB。

关于"4×100G RoCE 跨机比机内 PCIe 快"——**不成立**。网卡挂在 PCIe 上，
跨机带宽结构上被 PCIe 上界卡死，不可能超过机内。

### 6.1 哪些是部署期决定的，哪些是请求期决定的

**分区在加载时固定**（`pipeline_minimax_h3.py:305-306` 从 `model_index.json` 的
`_minimax_h3.partition` / `.tasks` 读进来），**一个进程只能服务一个分区**。

**task 是每请求选的**，走 `extra_params.task`，在 `_resolve_task`
（`pipeline_minimax_h3.py:444-461`）里解析：

- 没给 `task` 时的推断：`partition == "ref2va"` → `ref2va`；否则给了图 → `fl2va`；
  都没有 → `t2va`。
- 然后拿 `task` 去比 checkpoint 声明的 `supported_tasks`，**不在集合里直接 ValueError**，
  报文会把分区和支持列表都打出来。

所以"要 ref2va 就得另起一个实例"，不是配置问题，是权重问题。

### 6.2 fl2va 与 ref2va 的本质区别

不是"图生视频的两种叫法"，两者喂图的**通路不同**：

| | fl2va | ref2va |
|---|---|---|
| 图的角色 | **是输出的一帧**，从 keyframe 条件通道进 DiT | **参考素材**，从 Qwen 视觉块进文本编码器 |
| 代码位置 | `include_keyframe_cond=True`、`keyframe_frame_indices=[0]`（:980-982） | `minimax_h3_ref2va_presentation` 走 `pixel_values` / `image_grid_thw`（:594-603） |
| 可喂的模态 | 图（1 张） | 图 + 音频，或视频（可多段，带 block 时间戳，`input_has_audio` 时音频也进条件序列） |
| 默认帧数 | 209（`:479`） | 124（`:479`） |

两者都不给 `width/height` 时默认画布是 **768×1344**（`:494`）；fl2va 且给了图时
按图的宽高比推算，长边 768。

### 6.3 已知能力缺口（我们的实现，不是模型的限制）

1. **只支持 1 张图**——`:152` `MiniMax H3 currently supports exactly one image`
   （音频同理，`:176`）。
2. **fl2va 的关键帧位置写死在第 0 帧**——`keyframe_frame_indices=[0]`（`:981`）。
   官方支持"末帧"和"首+末帧"两种玩法，我们**目前给不出**：要开这两档，得让
   `keyframe_frame_indices` 跟着请求走（末帧 = `[num_frames-1]`，首尾 = `[0, num_frames-1]`），
   并放开 1 的图片数上限。

这两条是同一处改动的两面，没做。要不要做取决于产品是否需要"指定末帧"这个玩法。

- **僵尸进程会堆积**，`ps` 里一堆 `<defunct>`。要找真正活着的那个，按最大 `RssAnon` 挑。
- **SSH 有频率限制**，别用循环逐条 ssh；把活打包成宿主脚本，`docker exec -d` 一次丢进去。
- **容器时钟是 UTC**，看日志时间戳前先 `date`，别把"十秒前的日志"当成"卡住几小时"。
- 容器里**没有 `column`**。
