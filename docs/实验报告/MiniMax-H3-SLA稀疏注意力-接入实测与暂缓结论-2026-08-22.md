# MiniMax-H3 SLA 稀疏注意力：接入实测与暂缓结论（2026-08-22）

> 结论一句话：**backend 已跑通、加速真实（15 秒档 −23%），但手绘动画内容会出现运动方向反转，写实内容不会；最快档改用 v1.1 稠密，SLA 暂缓，等上游 v1.0 或后续研究。**
>
> 机器：dev-gpustack-a100-0041 ~ 0045（4×A100-PCIE-40G）。产物见 §7。
> 相关：`docs/user_guide/diffusion/attention_backends.md` §SLA_ATTN、
> `docs/实验报告/vLLM-Omni-MiniMax-H3-768p-Turbo-v1.1-与-SLA-稀疏注意力实测与选型.md`

---

## 1. 为什么做，做到哪一步

上游 2026-08-20 发布 `lightx2v/Minimax-h3-Turbo-SLA`：4 步蒸馏 FL2V 768p 适配器，与 SLA
（Sparse-Linear Attention, thu-ml, arXiv 2509.24006）按 85% 稀疏率联合微调。加速在 kernel
里不在权重里，所以我们实现了 `SLA_ATTN` backend（`vllm_omni/diffusion/attention/backends/sla_attn.py`，
纯 Triton，模型侧零改动，靠 H3 已发布的 `VideoTokenLayout` / `qkv_layout="BSND"` / `cu_seqlens`）。

跑通了，加速也是真的。但在**手绘动画**内容上出现了一个客观指标测不出、人眼一看就有的缺陷，
最终决定最快档不用它。

---

## 2. 加速与显存（同机、稳态、剔除冷启动首发）

| 片长 | SLA 0.85 | v1.1 稠密 | 提速 |
|---|---|---|---|
| 5 秒 | 67.3s / 59.1s | 75.0s / 66.5s | −10% / −11% |
| 10 秒 | 121.7s / 110.8s | 146.4s / 141.0s | −17% / −21% |
| 15 秒 | 174.6s | 226.6s | **−23%** |

（两列分别是手绘 fl2va 与真实拍摄 t2va 用例。）去噪段本身快 13~18%，稀疏不作用于 VAE 与封装，
所以墙钟收益被摊薄。显存多 0.3 GiB。片长越长收益越大：注意力是序列长度的二次项。

**稀疏率的最优值随片长变**：5 秒档 0.7 最优，15 秒档 0.85 最优（0.7 只快 5.6%）。
0.5 全程是负收益——保留 327/654 块已接近稠密，而块选择的固定开销一分不少，比 FlashAttention 还慢。

## 3. 缺陷：手绘动画的运动方向反转

**症状**：人物向一个方向走几步后，像倒放一样退回去。人眼明显，
**SSIM 与相邻帧差方差都测不出来**（帧内结构没坏，坏的是时间轴上的一致性）。

### 3.1 内容相关性（关键发现）

固定 1344×768 / 10 秒 / seed 42 / 4 步，五个用例各跑一遍：

| 用例 | 风格 | 运动 | 结果 |
|---|---|---|---|
| 手绘·野猪一家 | 动画 | 持续横向位移 | **反转** |
| 大丸家 promo 15s | 动画 | 分镜蒙太奇（每 3 秒切） | 未观察到 |
| 红衣女子横走 | 实拍 | 持续横向位移 | 未观察到 |
| 市集镜头平移 | 实拍 | 全局镜头运动 | 未观察到 |
| 汽车穿场 | 实拍 | 刚体匀速位移 | 未观察到 |
| 睡狐狸（几乎不动） | 动画 | 无 | 未观察到 |

**只有手绘动画 + 持续位移这一组合出问题**。最初以为触发条件是"持续定向运动"，
写实三条用例否掉了这个假设——**风格才是主变量**。

### 3.2 剂量响应

| 保留块 | 视频 | 音频 | 耗时 |
|---|---|---|---|
| 99%（sparsity 0.01） | 干净 | 有异常声 | 232.6s |
| 50% | 反转 | 正常 | 155.5s |
| 15%（0.85） | 反转 | 正常 | 121.6s |

99% 保留时视频干净 → **接线正确**（转置、缩放、LUT、padding 都通）。反转是丢块造成的。
但 0.5 已经比 v1.1 稠密（146.4s）还慢——**没有既不反转又比 v1.1 快的稀疏率**。

### 3.3 机制推测（未证实）

诊断运行（每层每步记录块选择行为，10 秒档 72 latent 帧 / 1211 key blocks / 85%）：

```
步间选择重合度(Jaccard): step1 0.629, step2 0.840, step3 0.862   → 步间是稳定的
选中键块的平均 |Δframe| : 24.6 帧（72 帧里随机取的期望约 24 帧）
落在 query 自身帧的比例  : 6.6%
```

即**块选择在时间维度上几乎等同于随机**，没有邻域偏好。原因是结构性的：packed 视频行按
`(t,h,w)` 排，每帧 1008 行，而一个块只有 64 行——**一个块只是某帧内约 1/16 的一条横带**，
不是时空邻域。相比之下 `rainfusion_attn` 会先把 token 重排成 (t,h,w) 时空块再选。

至于为什么只有手绘塌：手绘是大面积平涂、纹理极少，64 行 mean-pool 后各块特征彼此接近，
top-k 的第 k 名与第 k+1 名分数咬得很紧，选哪一批基本由数值噪声决定；实拍纹理丰富，
打分有区分度。**这一条只是推测，打分可分性的量化没来得及做**（诊断补丁已写好，见 §6）。

## 4. 尝试过的三个修法，都没解决

| 修法 | 依据 | 结果 |
|---|---|---|
| **BLKQ 64→128** | 模型卡运行配置是 `operator: sage2`，非 sm90 取 128/64 | **引入音频损坏**，已回退（见 §5） |
| **token_refiner 恒稠密** | 上游有 `refiner_attn_type` 开关且注释说明该分开 | 对反转无影响，音频无害 |
| **前缀键块恒定保留** | 前缀含首尾帧条件与音频，疑为运动锚点 | 无改善；且前缀有 77 块、占 181 预算的 43%，反而挤掉视频键 |
| **相邻帧同位置块恒定保留** | 把 RainFusion 的时空邻域先验补回来 | 未能消除反转 |

`start_step=1`（前一步保持稠密）实测代价 15 秒档 174.6→192.9s，仍比稠密快 16%，但也没解决。

## 5. 一次由本轮改动引入的回归（已修复）

把 BLKQ 从 64 改成 128 之后，**音频崩坏**：10 秒手绘用例（提示词写明"轻风、雪地脚步、无对白"）

| | LUFS | 真峰值 | 瞬时响度极差 |
|---|---|---|---|
| BLKQ=64（原版） | -41.3 | -29.1 dBFS | 10.2 LU |
| **BLKQ=128** | **-6.5** | **+3.4 dBFS** | **48.2 LU** |
| v1.1 稠密 | -42.0 | -29.7 dBFS | 14.7 LU |

比正常响 35 dB、削波、有突发噪声。2×2 单变量矩阵确认是 BLKQ 而非 refiner 改动引起。

**机制**：H3 的 packed 序列是 `[text | keyframes | 立体声音频 | video]`，音频约占 1%；
128 行的 query 块会**跨模态边界**，池化时音频行与视频行混在一个块里打分，
音频 query 实际按视频的相关性取键。BLKQ 已回退为 64，代码注释里记了这段实测。

**教训**：从上游抄参数时对齐了数字，没检查这个数字在我们的序列布局下意味着什么。

## 8. 重启这项工作时从哪儿接

1. **等上游 v1.0**，连同它的参考配置一起复现——包括 `operator: sage2` 那条 SageAttention2
   INT8 kernel（我们用的是 thu-ml 的 Triton 浮点版，数值路径不同，A100 支持需单独验证）。
2. **先量打分可分性**再改：记录 top-k 边界处第 k 与第 k+1 名的分数间隙（相对分数标准差归一化），
   对比手绘与实拍。若手绘的间隙显著更小，"平涂导致选择退化"就被证实，那么修法应指向
   **让打分有区分度**（换池化方式 / 换打分特征），而不是继续加先验。诊断补丁的写法见本轮
   记录：在 `_block_map` 的 top-k 之后插桩，逐层逐步写 jsonl。
3. **验收必须包含两项本轮补上的指标**：
   - **音频**：LUFS / 真峰值 / 瞬时响度极差（本轮的音频回归就是靠它定位的，SSIM 完全无感）；
   - **运动方向一致性**：目前只能靠人看，建议做一个光流主方向的符号翻转计数作客观代理。
4. **实验纪律**（本轮踩了四次）：单次只改一个变量；自驱动脚本启动前必须校验端口/容器/代码指纹；
   批量改代码的脚本每处替换都要 `assert`；跨机对比前先做交叉实验排除机器差异（实测机器间可差 8%）。
