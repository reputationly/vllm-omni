## 1. 合并做了什么

原策略：**上游拿结构、本仓拿产品行为**。

- H3 DiT：块类迁到上游新的 `minimax_h3_blocks.py`；本仓 pruned-AdaLN/folded-bias、`VDN_WINDOW_ATTN`（与上游 `VDNH3_ATTN` 并存且互斥报错）、`_diffusers_*` 权重名映射重挂到新位置。
- 采样器：上游把 `sampling.py` 重写为采样框架，本仓 Pika `renoise` 重新表达为 `vllm_omni/diffusion/sampler.py:sample_renoise`，每请求 generator 经 `sampler_object(name, generator=…)` 传递；`euler`/`res_multistep` 与上游逐字节一致；旧 `H3SampleSolver`/`create_h3_sample_solver` 全仓删除。
- H3 encoder：上游走标准 `load_weights(stream)` + NVFP4，本仓是"自读 safetensors + int8 档"，合并为统一消费器 `_consume_weight_stream`。
- 上游删除的模块（hidream_image、`engine/{mm_outputs,output_processor,output_modality}`、HiDream recipe、两个 e2e 框架）接受删除并核验无引用。
- 验证：全树 0 冲突标记、`compileall` 通过、`ruff F821/F811` 覆盖 2631 个改动 py 全绿、仓库自带 CI 检查（forbidden imports / SPDX / test marks / buildkite / torch cuda）全绿。

### 合并过程中修掉的 bug（都在新代码里，旧镜像不会有）

1. `tools/prepare_ci_telemetry.py` 要求 `BASE_IMAGE` 逐字等于固定 digest → workflow 默认值改成带 digest 的 0.33.0。
2. arm64 基座自带 `nvidia-cusparselt-cu13` 平台标记异常 → 保留 `uv pip check` 门禁，仅白名单这一条并 dump 元数据。
3. **`_consume_weight_stream()` 漏 `return loaded`** → H3-Image 启动即 `TypeError: 'NoneType' object is not iterable`（视频链路走自加载路径不受影响）。
4. **dynamo 把 `MiniMaxH3DiTBlock.layer_index` 当静态整数** → 28 层撞 `recompile_limit(8)` → 后面的层静默回落 eager，造成"每次容器启动 plateau 都不同、要 5–8 次请求才稳定"。修法 `torch._dynamo.config.allow_unspec_int_on_nn_module = True`。

## 2. GPUStack 合入路径（审计结论）

- 后端 `vLLMOmni 1.0.0` 的镜像只在 `inference_backends.version_configs["1.0.0"].image_name` 一处，且是**浮动 tag** `arm64-a100-latest`。
- 每模型差异只有：`--deploy-config=/deploy-configs/*.yaml`（**烘进镜像**）、模型级 `env`、`backend_parameters`；`models.image_name` 支持**模型级镜像覆盖**（现网原本全为 NULL）。
- 因此上线有两条路：
  - **全局**：把 `latest` 指到新 tag → 20+ 个 vLLMOmni 模型下次重启一起换代（风险大，vLLM 0.33 对 TTS/音频类有未知风险）；
  - **推荐**：**模型级 `image_name` 覆盖**（本次 H3-Image 就是这么上的），其它模型完全不受影响，可单模型回滚。
- 部署档烘焙在镜像里，改一行参数也要重出包 —— 这是流程上的摩擦点，建议后续改成外挂卷。

## 8. tts2 金丝雀 OOM 的确诊（不是镜像问题）

`breeze_tts_2_throughput.yaml` 两个 stage 都落在 GPU0（`devices: "0"`，0.65 + 0.15 = 0.8 利用率）。金丝雀里 stage0 占 14.28 GiB、stage1 到 25.05 GiB 时 OOM（其中 22.7 GiB 是 CUDA Graphs 私有池，stage1 `max_num_seqs: 32` × `max_model_len: 32768` 的图池很大）。现网同配置能跑，说明这是"2 stage 挤一张 40 G 卡"的**边缘状态**，对进程内存布局/图池时序敏感，不是新镜像引入的。
→ 建议：给 tts2 增加 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` 或把两 stage 拆到两张卡，再补 A/B。

## 9. tts2 补测完成（2 卡配置，同机 A/B）

单卡把两 stage 挤在一起会 OOM（见 §8），于是把部署档里 stage1 的 `devices` 改成 `"1"`（只读 bind-mount 覆盖，不改镜像），在 gpu43 上对同一份配置跑新旧镜像：

| | 冷启动 | 预热 (s) | 中位 | 峰值 |
| --- | --- | --- | --- | --- |
| 旧镜像 `8838e733` | 2.948 s | 0.983 / 0.905 / 0.910 | **0.908** | 42406 MiB |

→ 修复包 **快 11.3%**，峰值持平（+4 MiB）。这是五个现网 vLLMOmni 模型里唯一"明显更快"的一个。
