## 1. 背景结论（为什么这样合）

- 这个仓一直在跟上游。8 月以来已合过 6 次。最近两次：9-27（`884a45d01`，基座 vLLM 0.30）进 `origin/main`；10-04（`693f5823a`，合入上游 `c9bee166f` 的 84 个提交，14 个冲突逐个审阅）完成在 `merge/upstream-20261004` 分支上，尚未进 `origin/main`。**本轮从 10-04 那次的结果接着合**，属于常规同步，**用 merge，不用 rebase，也不重建分支**。
- 10-04 那轮自带八层审计记录（冲突标记 0、`compileall` 通过、`ruff` F821/F811/F401 全绿、三方整文件判定本地新增丢失 0、A100 定制 16 项逐符号存活），独立复核也对得上，因此本轮直接继承其结果，见 §5.0。
- 本轮有三处特殊情况：
  1. **Qwen-Image-2.1 的代码来源变了。** 我们之前合入的是上游一个未合的分支（#7759）。上游 10-07 正式合入的是重写过的 #8099，Qwen-Image-2.1-Turbo（#8699）又是在 #8099 的基础上做的。所以本轮 Q21 统一改用上游代码，再把我方的 A100 定制以补丁形式补回去。
  2. **H3 的 VDN 现在有两套实现。** 上游 #8439 新增了 `VDNH3_ATTN`（`vdnh3.py`），我方现网用的是 `VDN_WINDOW_ATTN`（`vdn_hybrid.py` 加 `vdn_window_attn.py`）。两套都实现 OpenVDN，都加载 8 步 DMD 学生模型。**本轮两套都保留**，冲突块按"两条分支并存、由后端名选择"来解决。改不改用上游那套，等 §6.3 的两臂对照出结果后单独决定，不在本轮合并里做。
  3. **vLLM 基座要升级。** 上游已在 `0b0d2d700` 把基座升到 vLLM 0.31，我们还是 0.30。本轮跟着升级。

## 2. 合入原则（遇到冲突时依次套用，前一条能判定就不看后一条）

1. **现网行为不能变。** 现网 5 个模型的部署档、请求参数和输出要保持不变。具体要求：同 seed 下逐位一致；如果有意改变了数值路径，必须在提交说明里写明原因，并通过 §6 的画质验收。
2. **A100 定制必须保留**（清单见 §3）。即使上游有同名或同目标的机制，也必须先用仪器实测上游实现是否覆盖了我们的场景，才能删除我方实现。复盘里记过一次反例：上游的 model-level offload 其实不卸载 VAE，而我们据此删掉了自己的卸载开关。
3. **同一目标、上游实现更好、且不影响 A100 的，取上游。** 例如 Q21 的主体代码、wan_vae_fastpath、adalayernorm。
4. **双方各做了不同的事，两边都保留（取并集）。** 比如注册表、import、新字段、新的 hook。
5. **上游删除或搬走的东西：** 先在固定的上游 hash 上找新位置（`git grep <关键字> $UP`，`$UP` 见 §4），把我方的增量搬过去。只有当我方改动仅是元数据（比如 SPDX 版权头）时，才直接接受删除。
6. **按符号解冲突，不按冲突块顺序硬啃。** 大文件先把符号分成四类：我方独有、只有我方改过、双方都改过、上游删除或搬走（方法见复盘 §2.4）。
7. **解冲突的写法：** 要么在内存里改好后一次写出，要么用 `git checkout --merge <file>` 拿回干净的冲突状态重来。**不要先写盘再回退。**
8. **通用的 bug 修复**（与 A100 和业务无关），合完以后提 PR 给上游，提交后登记进 8-23 方案 §7 的分叉清单。

## 4. 操作步骤

```bash
cd ~/repos/vllm-omni
git fetch origin && git fetch upstream
git config rerere.enabled true          # 8-23 方案 §6.4
B=sync/upstream-$(date +%Y%m%d)
# 起点分支必须带 origin/ 前缀：新克隆里只有 origin/merge/upstream-20261004，
# 裸名会报 fatal: 'merge/upstream-20261004' is not a commit。
git checkout -b "$B" origin/merge/upstream-20261004
# 固定上游 hash 再合，避免上游继续变动导致下一个执行者拿到不同的集合。
UP=74ba8ab69                            # 写本手册时的 upstream/main；见头部"上游会继续变"
git -c merge.renameLimit=5000 merge --no-ff "$UP"   # 预期 50 个冲突文件
git diff --name-only --diff-filter=U > /tmp/conflicts.txt
```

> **`UP` 与头部记录不同时，先重跑一遍冲突集确认仍是 50 个**，再往下做。两种统计写法，按 git 版本选：
>
> ```bash
> # 写法 A（git >= 2.38）：不落盘
> git merge-tree --write-tree --name-only origin/merge/upstream-20261004 "$UP" \
>   | grep -oE 'CONFLICT \([a-z/]+\)' | sort | uniq -c      # 期望 33/content 9/add-add 8/modify-delete
>
> # 写法 B（任意 git 版本，前几轮一直用的就是这个）：临时 worktree 里真合一次再中止
> git worktree add /tmp/conflict-probe origin/merge/upstream-20261004
> ( cd /tmp/conflict-probe && git -c merge.renameLimit=5000 merge --no-commit "$UP" >/dev/null 2>&1
>   git diff --name-only --diff-filter=U | tee /tmp/conflicts.txt | wc -l
>   git merge --abort )
> git worktree remove --force /tmp/conflict-probe
> ```
>
> 写法 A 需要 **git ≥ 2.38**（低版本会报 `fatal: unknown rev --write-tree`）。拿不准就用写法 B。

处理顺序：先做机械类的（§5.1），再做 Q21（§5.2），然后 H3（§5.3），最后其余（§5.4）。每处理完一类就 `git add` 这一类文件。全部处理完后先跑 §6.1 的八层审计，审计通过再 commit。

**A4 —— `denoise_loop.py` 换成 solver 抽象**

上游 #8378（`b65f97bc4`，res_multistep）已包含在 10-04 里，而 `origin/main` 没有它。变化是**调用路径**的替换，不是删几个实参：

- **`origin/main`**（现网现状）：`denoise_loop.py:543`、`562` 直接调 `minimax_h3_euler_eta0_step(..., sigma_curr=s_v, sigma_next=s_v_next)`
- **起点分支 / 10-04**：先 `video_solver = create_h3_sample_solver(sampler, sigmas_video)` / `audio_solver = ...`（`denoise_loop.py:476-477`），再 `video_solver.step(video_rows[update], x0_video, step)` / `audio_solver.step(audio_rows[audio_update], x0_audio, step)`（`denoise_loop.py:552`、`570`）
- 因此 `s_v_next`/`s_a_next` 这两个**局部变量**不再有人读，随之删除。注意 `sigma_curr=`/`sigma_next=` 并**不是**死参数 —— `H3SampleSolver.step` 内部照旧传给 `minimax_h3_euler_eta0_step`（`sampling.py:64`）。

**从 10-04 起步时本轮不会重现**（`denoise_loop.py` 在 §5.0 的继承清单里）。

> 若改成从 `origin/main` 起步，要按上面的方式换成 `solver.step` 调用并删掉这两个局部变量，**不是**只删实参。

**2026-10-14 复核更正：这一处在 euler 路径上是逐位重构，不改数值。** 原先写成"已知会改变现网 H3 数值路径"是过度概括——A4 正文本来就写对了（`sigma_curr`/`sigma_next` 照旧传进 `minimax_h3_euler_eta0_step`）。下面的 0–3 已按真机实测改写，仍需单独验收，但验收目标是**证明它没改**，不是容忍它改了：

0. **先摆正前提**：生产镜像是基于 `origin/main` 的（见 §6.2），而 10-04 已经带进来 85 个提交 —— **对现网来说它们全是新代码**。会碰到 H3 的几处，连同 2026-10-14 的真机复核结论：
    - **solver 切换 —— 不改数值（逐位）**。`H3SampleSolver.step` 在 `name == "euler"` 时直接调 `minimax_h3_euler_eta0_step(state, denoised, sigma_curr=curr, sigma_next=nxt)`，其中 `curr, nxt = self.sigmas[step:step+2]`，与旧代码 `sigmas_video[step], sigmas_video[step+1]` 同函数、同实参、同运算顺序（`sampling.py` 的模块 docstring 明说 "preserve its exact floating-point operation order"）；`self.sigmas` 的元素是原生 Python `float`，`tuple(float(s) …)` 不引入误差。实测 6 条 schedule（含两份现网档的 vdn8，及 4/20/40/50 步）× 全部 step × 3 种 shape，`torch.equal` **全部为真**。只有 `res_multistep` 会改数值，而现网进不到那条分支（见 §6.3 的通过标准）。
    - **`flash_attn`/`fa` —— A100 上不改数值**。`attention/backends/utils/fa.py` 的改动是**纯新增**（Blackwell 的 FA4 分支、ROCm 的 AITER 分支、新的 FA3 直调函数），非 Blackwell 的 CUDA provider 选择链一字未动，所以 `vdn_window_attn.py` 直接 import 的 `flash_attn_varlen_func` 前后绑定到同一个实现；`attention/backends/flash_attn.py` 把 `forward` 里的内联分支换成 `_normalize_flash_attention_metadata`，实测 12 组 metadata 的路由判定（piecewise / packed-varlen / masked-varlen / dense）与旧代码**逐条一致**，唯一发散条件是 `extra["attention_mask_mode"]` 被发布，而**全仓没有任何 producer 发布这个键**（只有 `abstract.py:251` 的约定注释和 `flash_attn.py` 的消费者）；FA4 稠密分支在 A100 上 `IS_FLASH_ATTN_4` 恒为 `False`，不进入。`VDN_WINDOW_ATTN` 的窗口分组本就**绕开** `forward`，直接调 `flash_attn_varlen_func`，只把稠密回退交给 `FlashAttentionBackend`。
    - `pipeline_minimax_h3.py`（+498，主要是 #8322 超分）—— `latent_upscaler` 为 `None` 时不生效；
    - `model_executor/models/minimax_h3/reference_video.py`（#8253，见 P2）—— 新开关默认关闭；关闭时真机上 5 组参考视频几何**逐位复现**，不改数值；
    - #7355 的视频传输改动（`video_api_utils.py` +44）。

### 6.4 VDN 两臂对照（不挡本轮合并，单独出报告）

先说清楚前提和限制：

1. **上游 VDN 只支持 fl2va**。`vdnh3.py` 第 292–293 行：partition 不是 fl2va 就报错。所以无论对照结果如何，**ref2va 都只能继续用我方实现**。对照只覆盖 fl2va；就算对照结论是"改用上游"，也只是 fl2va 改用上游，我们仍然要长期维护两套。决定前要把这个维护成本算进去。
2. **checkpoint 用原版 BF16 `stage-dmd-step-250`**，不用我方的 INT8 剪枝档。原因：
   - 上游的 `to_out_linear` 传的是 `quant_config=quant_config`（第 601–609 行），是按在线量化写的；
   - 我方离线 INT8 档的 `ignored_layers` 来自源 checkpoint，里面没有 VDN 投影，上游那一臂可能连加载都过不了（这个后果是推断，未实测）。
   - 如果用 INT8 档对照，失败原因跟画质无关，会误判成"上游不行"。
3. **两臂都用相同的显存口径**：1080p、15s、冷态和热态分开。我方这一臂按现网配置跑，`VLLM_OMNI_VDN_KV_GATHER_BUDGET_MB=192`。上游 `vdnh3_attn.py` 第 169 行无条件地 `key.index_select(1, key_rows)`，一次把整组 K/V 都物化出来，没有预算控制。1080p/15s 在 40G 上，最可能先 OOM 的就是这里。

指标：SSIM/PSNR、逐帧目视、冷态和热态耗时、每卡显存峰值。

结论规则：

- **fl2va 改用上游**需要同时满足三条：画质相当；耗时不超过我方 +5%；在 1080p/15s 下补上下面三个补丁后不 OOM。三个补丁是：
    - (1) 合并 all-reduce；
    - (2) KV gather 显存预算（移植 `VLLM_OMNI_VDN_KV_GATHER_BUDGET_MB`）；
    - (3) 离线 INT8 档的兼容（VDN 投影要能加载）。

  三个都做完、都通过，才在下一轮切换；三个补丁都提 PR 给上游。
- 有任何一条不满足：fl2va 也保留我方实现，把差距写进 8-23 方案 §7。
- ref2va 不受对照结果影响，始终用我方实现。
