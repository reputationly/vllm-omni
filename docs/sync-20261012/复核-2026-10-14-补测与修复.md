## 5. §5.3 AdaLN 剪枝 × CPU stager：**修复前不成立**（新发现）

手册 §5.3 原文：

> 保留我方的 pruned/folded_bias 加载；同时加入上游 #7989 的精确 AdaLN 权重卸载（CPU stager）。
> **必须验证两者能叠加**：在剪枝档加 offload 的配置下，`MiniMaxH3AdalnProj._project` 的结果要和合并前逐位一致。

现有 `test_adaln_cache_device.py` 覆盖不到：它构造的 arch 没有 `adaln_rank`（即非剪枝），
而且 `hardware_marks(res={"cuda": ["H100","B200"]})` 在 A100 上直接 skip。

### 5.1 真机探针与结果

探针（`probe_adaln.py`）用与生产一致的分布式初始化构造剪枝档 `MiniMaxH3AdalnProj`
（`adaln_rank=64`、`time_table_size=8`），在**同一组输入张量、同一份权重**下比较三条路径：

| 路径 | 修复前 | 修复后 |
| --- | --- | --- |
| `premerge`（`origin/main` 的字面公式） | — | 基准 |
| `resident`（剪枝，无 offload） | BIT-IDENTICAL | **BIT-IDENTICAL** |
| `offload`（剪枝 + offload） | **RuntimeError** | **BIT-IDENTICAL**，且调用后权重确认回到 CPU |

修复前的报错：

```
RuntimeError: Expected all tensors to be on the same device, but got mat2 is on cpu,
different from other tensors on cuda:0 (when checking argument in method wrapper_CUDA_mm)
```

### 5.2 根因（两处，都在 `_project`）

1. 剪枝分支在 `self._weight_stager.load()` **之前**就 return。offload 档下 `self.linear` 是
   `with torch.device("cpu")` 分配的主机副本，CUDA 输入进 `CUDA_mm` 直接报设备不一致。
2. 即使把 `load()` 补在 linear 调用外层，`finally` 里的 `offload()` 会在
   `x.float() + self.folded_bias` **之前**把权重搬回主机；而 `_apply` 的 `keep_on_host`
   同样把 `folded_bias` 留在主机，于是加法又跨设备。

### 5.3 改法（`aa72a0d10`）

* staging 抽成覆盖整次投影的信封 `staged(compute)`，剪枝分支把 matmul 与 `folded_bias` 加法一起放进去。
* staging 组由 `self.linear` 换成 `self`：`PinnedModuleStager` 本就按「模块的参数 + 缓冲区」快照，
  剪枝档的 `folded_bias` 与 linear 同属一次投影，必须一起搬。
* 未剪枝 + offload 路径语义不变：`silu` 仍在 staging 之外计算，`load`/`offload` 的配对与顺序保持原样。

### 5.4 可达性

`default_offload_adaln` 要求 `get_device_capability(...) == (12, 0)`，即 SM12.0（Blackwell）才默认开；
A100（SM8.0）需显式在 cache config 里设 `minimax_h3_adaln_offload=True`。
放行条件只挡了 `quant_config is not None` 与 `conflicting_offload`，**没有挡剪枝档**。
也就是说：BF16 剪枝档 + 显式开 offload（或在 SM12.0 上跑 BF16 剪枝档，此时默认就开）会直接崩在第一次投影。

## 6. §6.3「已知会改数值的三类」：三类全部实测排除

§6.3 原文在同一句里既把 solver 切换列为"已知会改 H3 数值路径"，又规定"差异来自 solver 切换算不通过"，
构造上不可满足（solver 切换是 §5.0 A4 主动采纳、`denoise_loop.py` 在继承清单里）。
2026-10-14 逐类做了实测，结论是**三类都不改数值**，矛盾随之消失。

| 声称的已知变化 | 实测结论 | 依据 |
| --- | --- | --- |
| solver 切换 | **不改数值（逐位）** | 见 §5；6 条 schedule × 全部 step × 3 shape，`torch.equal` 全真 |
| `flash_attn`/`fa` | **A100 上不改数值** | 见 §6.1 |
| #8253 P2 参考视频不放大 | **不改数值** | 开关默认关闭（`reference_video.py:82`）；关闭时真机 5 组参考视频几何逐位复现 |

会改数值的 `res_multistep` 分支现网进不去，两道硬护栏：
`vdnh3.py:325` 拒绝非 euler 的 sampler；`pipeline_minimax_h3.py:3090`/`4413` 对
「res_multistep + 固定蒸馏 schedule」直接报错。`normalize_h3_sampler(None)` 默认即 `"euler"`，
两份现网 H3 部署档也都没有 `sampler` 字段。

同时关掉 §5.0 A4 第 2 条的可用性风险：`res_multistep_coeffs` 新增的严格校验
（长度 ≥2、`[0,1]`、严格递减）对 6 条真实 schedule 全部通过。

### 6.1 `flash_attn`/`fa` 为什么在 A100 上不改数值

`vdn_window_attn.py` 是我们自己的文件（`e872a7a19`），它**直接依赖**上游改过的两个文件
（`:44` 导入 `FlashAttentionBackend`、`:122` 与 `:290` 调用 `flash_attn_varlen_func`），
所以这条必须实测，不能靠"上游只是改了内核"带过。

1. **`attention/backends/utils/fa.py` 的改动是纯新增**：新增 Blackwell 的 FA4 分支、ROCm 的 AITER 分支、
   新的 FA3 直调函数（`flash_attn_3_varlen` 等）与两个模块级 flag。**非 Blackwell 的 CUDA provider 选择链
   一字未动**，所以 `flash_attn_varlen_func` 前后绑定到同一个实现（A100 `capability.major == 8`，
   `_is_blackwell()` 为 False，走 else 分支的 Candidate 2–5）。
2. **`backends/flash_attn.py` 的路由判定逐条等价**：`forward` 把内联分支换成
   `_normalize_flash_attention_metadata`。用探针把旧逻辑（从 `origin/main` 逐句复刻）与新逻辑对拍
   12 组 metadata：

   | case | 旧(origin/main) | 新(HEAD) | 一致 |
   | --- | --- | --- | --- |
   | no-metadata / mask-all-true | dense | dense | ✅ |
   | mask-with-padding | masked-varlen | masked-varlen | ✅ |
   | packed / packed-with-mask | packed-varlen | packed-varlen | ✅ |
   | piecewise / piecewise-with-packed-keys | piecewise | piecewise | ✅ |
   | extra-unrelated-key | dense | dense | ✅ |
   | incomplete-packed | raise ValueError | raise ValueError | ✅ |
   | mask-none-published | masked-varlen | **dense** | ❌ |
   | mask-padding-published | dense | **masked-varlen** | ❌ |

   **可达输入的发散项 = 空。** 唯一发散要求 `extra["attention_mask_mode"]` 被发布，而全仓
   **没有任何 producer 发布这个键**（只有 `abstract.py:251` 的约定注释与 `flash_attn.py` 的消费者）。
3. **FA4 分支在 A100 上不进入**：`IS_FLASH_ATTN_4` 恒为 `False`。
4. **`VDN_WINDOW_ATTN` 的窗口分组本就绕开 `forward`**，直接调 `flash_attn_varlen_func`；
   只有稠密回退交给 `FlashAttentionBackend`。

据此已在手册中把 solver 与 `flash_attn`/`fa` 从"已知会改数值"列表移除，接受侧补入
"attention 内核实现"，不合格侧收敛到"我方的契约代码"（`main` 的 `9e66c4e1a`）。

## 10. H3 音频首请求偏差：根因与已验证的修法（2026-10-14 真机）

### 10.1 症状（本次重测，非引用旧笔记）

同 seed、同 prompt、同输入，**服务启动后第一个请求的音轨与后面不同**；第 2/3/4 个请求彼此逐位相同。**视频流每次都逐位相同。**

| 镜像 | 请求 | 视频流 | 音频流 |
| --- | --- | --- | --- |
| baseline（origin/main, v0.30） | cold（第 1 个） | `b86dd2f0…` | `92df960c…` |
| baseline | hot（第 3 个） | `b86dd2f0…` | **`92df960c…`**（相同） |
| **HEAD（v0.31）** | cold（第 1 个） | `12c2b725…` | `04a5ef68…` |
| **HEAD** | run2 / run3 | `12c2b725…` | **`551c55ed…`** |

**baseline 上 cold == hot，HEAD 上 cold ≠ run2 == run3 ⇒ 这个偏差不是既存的，是本轮合并引入的。**

量级：差异样本占比 99.9%–100%，平均 |Δ| ≈ 0.006–0.007（满幅 1.0，≈ −44 dBFS），最大 |Δ| 达 0.066–0.252（内容相关）。

### 10.2 根因：定位到 checkpoint 自带音频解码器的「进程内首次调用」

在同 seed 连发 3 个请求、并在 `MiniMaxH3AudioVAE.decode_latent` 上打点（记录 latent 哈希、波形哈希、8 个 torch 全局开关、解码器参数设备/精度）：

```
call 1 : latent=8e28b23be324 → waveform=c39449be735c
call 2 : latent=8e28b23be324 → waveform=bd7fa48c7c7d
call 3 : latent=8e28b23be324 → waveform=bd7fa48c7c7d
```

* **输入 latent 逐位相同**（4 个 rank 也相同）⇒ 文本编码器 / DiT / 噪声 / solver 全部确定性。
* **只有波形不同**，且只差在第 1 次。
* **torch 的 8 个全局开关在全部调用、全部 rank 上只有一种取值**（`matmul_tf32=False, cudnn_tf32=True, cudnn_enabled=True, cudnn_deterministic=False, benchmark=False, f32_precision=highest, sdp=全开`）⇒ **不是环境状态被改**。

把音频 VAE 单独加载（605 MB，无 DiT），同一进程内对同一 latent 连解 4 次，**秒级复现**：

```
decode call 1 -> 846d2561e36abaf8
decode call 2 -> ca5410915809fdde
decode call 3 -> ca5410915809fdde
decode call 4 -> ca5410915809fdde
distinct outputs: 2
```

⇒ **根因是 `self.remote.decode()`（checkpoint 自带、`trust_remote_code`、fp32）在一个进程里的首次调用会产出不同的结果**，与输入、权重、后端开关都无关。

### 10.3 被证伪的三个假设

| 假设 | 结论 | 证据 |
| --- | --- | --- |
| 环境精度状态（TF32 / cuDNN）在首调用时不同 | **证伪** | 8 个开关在全部调用/rank 上只有一种取值 |
| 是 cuDNN/TF32 的非确定性导致 | **证伪** | 把 `decode_latent` 包进 `_AudioVAEDeterminismContext`（cudnn 关、TF32 关、deterministic 开）后**仍然** call1 ≠ call2 |
| `weight_norm` 首次前向改了有效权重 | **证伪** | 有效权重指纹在任何前向之前 / call1 之后 / call2 之后都是 `7f63392e874dc76f` |

### 10.4 已实测的修法：一次极小的 warm-up 解码

```
reference settled value: ca5410915809fdde          # 未预热时第 2 次的值
warm-up(remote.decode, len=1) took 0.208s
  next 3 real decodes: ['ca5410915809fdde', 'ca5410915809fdde', 'ca5410915809fdde']
  all equal: True  equals settled: True
```

要点：

* 预热只需 `self.remote.decode(zeros(1, latent_channels, 1))`，**0.208 s**，与生产时长/分辨率无关（换一个 shape 预热同样有效）。
* 预热后每次真实解码都等于「稳定值」，**不改动稳态输出**——它只是让第一个请求不再是个例外。
* 与 `pipeline_auk.py:331` 的做法同构（该文件把「引擎的 dummy 请求到不了这个 pipeline」记在注释里，改用管线内局部预热）。

### 10.5 为什么不能走「打开引擎自带 warm-up」这条路

H3 的 `dummy_run_num_frames = 0` 是有原因的，把 `_make_dummy_request` 的预热打开会让**服务起不来**：

```
dummy run to warm up the model (1/1: 512x512, model-default frames)
Dummy run failed: checkpoint partition 'fl2va' supports ['fl2va', 't2va'], got task='ref2va'
→ /ready = 000
```

链路：`_make_dummy_request` 对任何声明支持音频输入的模型都注入一段音频 → `_resolve_task(None, multi_modal_data)` 见 `audio is not None` 且 `audio_mode != "lock_source"` → 返回 `"ref2va"` → fl2va 分区的 `supported_tasks` 只有 `{'fl2va','t2va'}` → 抛错；而 `run_startup_warmup` 捕获后 `self.close()` 再抛出，**引擎直接关闭**。

### 10.6 尚未确定的

* 解码器内部**究竟缓存了什么**还没定位（权重没变、与 shape 无关、跨设备开关无关）。目前只到「首次调用会进入一个与后续不同的路径，且这个路径只影响波形数值」。定位它需要读 checkpoint 的 `dac_*` 解码器实现（`/nfs-data/models/MiniMax-H3/FL2VA/audio_vae/`）。
* warm-up 放在哪里最合适（`MiniMaxH3AudioVAE` 里惰性做一次 / 在管线组件加载后做）以及是否需要按 `encode_only` 分支设防，待定。
* **修与不修的取舍**：本次实测证明修法不改稳态数值，只消掉首个请求的异常；但「首个请求的音轨会变」本身就是行为变更，按 §6.3 需要重新过一遍冷态验收。

### 10.8 修法在真机上**验收失败**（重要，已回滚）

§10.4 那个 warm-up 修法按「惰性一次、在 `decode_latent` 入口」实现了，并补了 5 个单测
（机制层面：首次多一次解码、后续不再预热、探针与请求同设备同 dtype、预热失败不致命、
`encode_only` 不受影响）——**单测 5 passed**，隔离环境里也逐位验证过。

**但在真机冷态三连发上没通过。** 同一份代码、同一档、同一台机：

| 运行 | run1 音频流 | run2 音频流 | run3 音频流 |
| --- | --- | --- | --- |
| 未加修法 | `291753459d5f71ad` | `a4efb845430a540b` | `a4efb845430a540b` |
| 加了修法 | `291753459d5f71ad` 首次 | 见下 | 见下 |

（表意：两次运行都是 run1 独立、run2 == run3，**修法没有改变形态**。）

为避免"修法到底跑没跑"这种推断，把 warm-up 本身也打了点。原始日志顺序（pid 已省略）：

```
warmup_in   probe_shape=[1, 32, 1] device=cuda:0      ← 4 个 rank 都执行了
warmup_out  out_shape=[1, 1, 800]  out_md5=c87cebfd…  ← 没有 warmup_failed
decode_in   call=1
decode_out  call=1  wf=441400195b00                   ← 仍然与 call2 不同
decode_in   call=2
decode_out  call=2  wf=8767dab2de0f
decode_out  call=3  wf=8767dab2de0f
```

即：**预热确实在第一次真实解码之前、在同一实例、同一 CUDA 设备上成功执行了，但首次解码仍然不同。**
（latent 三次都是 `0cd5a811dddd`，参数设备三次都是 cuda：全一致。）

**结论：该修法在目标环境无效，已回滚，不进分支。** 单测文件一并删除。

### 10.9 为什么隔离环境会"骗人"

隔离探针（单独加载音频 VAE，无 DiT / 无服务）与服务并不等价，本文记录这个差异以免后人重走：

| 构造 | 现象 | warm-up 是否有效 |
| --- | --- | --- |
| 直接 `.to(cuda)`，`decode_only=False` | call1 与后续不同 | **有效**（后续全部等于稳定值） |
| `load_device=cpu` + `PinnedModuleStager`，`decode_only=False`，带 load/decode/offload 循环 | call1 与后续不同（复现服务症状） | **有效** |
| `load_device=cpu` + stager，**`decode_only=True`（管线实际取值）** | **三次全同，根本不复现** | 无所谓 |
| 真机 4 rank 服务，`decode_only=True` | call1 与后续不同 | **无效** |

也就是说：隔离里能复现的那个「进程内首次 `remote.decode` 不同」是真的，但**它不是服务里那个现象的完整机制**；
服务里还有一层我尚未复现的状态（可能与 CPU-offload 暂存、4 rank、或组件加载顺序有关）。
单靠"先解一次"消不掉它。
