## 三、冷热不一致问题：已完整定位（严重性低）

### 现象
同一个 seed，**服务启动后第一个请求**与后续请求出片 md5 不同；第二个请求起完全稳定。
（共 7 次独立复现，含关编译实验）

### 逐层证据（决定性）

| 层级 | 检测手段 | 结果 |
|---|---|---|
| 送入模型的初始噪声/条件噪声/步数/几何 | `_build_denoise_inputs` 打张量 sha256 | ✅ 8 行逐字符相同 |
| DiT 8 步去噪潜变量（视频+音频） | `denoise_loop` 每步打哈希 | ✅ 每步 8 条记录全部相同 |
| **解码后画面（124 帧）** | 解码 mp4 后对像素做 sha256 | ✅ **`3800dc92ea8163602cad` 两侧相同**，逐帧绝对差 **0.0000** |
| 纯视频流字节 | `ffmpeg -c copy -map 0:v` | ✅ **完全一致** |
| **音频流字节** | `ffmpeg -c copy -map 0:a` | ❌ 不同 |
| 音频波形 | 解码 s16le/32kHz | ❌ 98.9% 样本不同；mean=137、max=2571（满量程 32767） |

**⇒ 画面 100% 逐位一致；差异 100% 在音轨，幅度平均 0.4%、峰值 7.8%（人耳不可闻）。**

### 根因链条
```
H3 pipeline 声明 dummy_run_num_frames = 0  →  跳过启动预热
        ↓
首个真实请求承担"首次调用"的 kernel 选择代价
        ↓
音频 VAE（checkpoint 自带 fp32 代码）走了不同 kernel 路径
        ↓
仅音轨微小差异 → 文件 md5 不同；画面完全一致
```

### 为什么预热是关的（实验发现）
把 `dummy_run_num_frames` 改成 120 后：
```
dummy run to warm up the model (1/1: 512x512, model-default frames)
Dummy run failed: checkpoint partition 'fl2va' supports ['fl2va','t2va'], got task='ref2va'
```
**dummy 请求用错了 task（ref2va），预热必然失败 → 上游只能关掉。**（该实验已回退）

### 是否合并引入
`dummy_run_num_frames = 0` 与 `run_startup_warmup` 在 **10-04、origin/main、HEAD 上全部存在** → **既有设计**。
但基线冷热 md5 相同、新镜像不同 → **相对基线仍是新现象**（vLLM 0.31 下音频解码器首次 kernel 行为变化）。

### 已试无效
`CUBLAS_WORKSPACE_CONFIG=:4096:8` 实测无效。

### 处置选项
| 方案 | 代价 | 效果 |
|---|---|---|
| A. 修 dummy task 解析 + 启用预热 | 启动 +约 2 分钟 | 严格满足"同 seed 逐位一致" |
| B. 记录为已知现象放行 | 无 | 画面 100% 一致，音轨差异不可闻 |

### 🔍 Qwen 分辨率异常 —— 根因定论（既有缺陷，非本轮合并引入）

**根因**：`/v1/images/generations` 在 `api_server.generate_images`（行 2218）里
把尺寸写进了 `extra_body["size"]`，但调用下游时**没有把它作为 `size=` 参数传出**：

```python
# api_server.py:2265-2269
if request.size is not None:
    width, height = parse_size(request.size)
    _check_max_generated_image_size(app_state_args, width, height)
    extra_body["size"] = request.size          # 只放进 dict

# api_server.py:2301 —— 调用时没有 size= 参数
generation_result = await chat_handler.generate_diffusion_images(
    prompt=request.prompt,
    extra_body=extra_body,
    request_id=gen_request_id,
    raw_request=raw_request,
    arrival_time=request_timestamp,
)

# serving_chat.py:3460 —— 于是保持默认
size: str = "auto",
```

`extra_body["size"]` 只在另一条链路 `_resolve_height_width_from_extra_body` 里被消费，
而那条链路属于 `_prepare_diffusion_image_request` / `_create_diffusion_chat_completion`
—— 即 **`/v1/chat/completions`** 入口，不是 `/v1/images/generations`。

**跨提交核验（四个提交完全一致）**：

| 提交 | 写 `extra_body["size"]` | 调用传 `size=request.size` |
|---|---|---|
| 10-04（合并起点） | 有 | 无 |
| 74ba8ab69（上游） | 有 | 无 |
| origin/main（现网） | 有 | 无 |
| HEAD（本轮结果） | 有 | 无 |

**⇒ 结论：既有缺陷，不是本轮合并引入。** 现网行为与合并后一致，不构成同步阻塞。

**实操建议**：要指定分辨率时走 `/v1/chat/completions`（该入口能正确解析 `size`）；
`/v1/images/generations` 的 `size` 仅被校验、不被应用。

**对 §6.3 的影响**：手册列的「t2i 2048²/2752×1536」需用 chat completions 入口重测，
不能用 `/v1/images/generations`。

### 🎉 根因结论的**决定性验证**

对照实验（同一模型、同一部署、同一时刻）：

| 入口 | 请求 `size` | 实际出图 | 结论 |
|---|---|---|---|
| `/v1/images/generations` | `2048x2048` | **1024×1024** | ❌ 尺寸被丢弃 |
| `/v1/images/generations` | `2752x1536` | **1024×1024** | ❌ 尺寸被丢弃 |
| **`/v1/chat/completions`** | **`512x512`** | **512×512** | ✅ **尺寸正确应用** |

（chat completions 请求：HTTP 200，452,555 字节，返回 1 张内嵌图，实测 **512×512**）

**⇒ 根因结论成立**：
- `/v1/images/generations` 调用 `generate_diffusion_images` 时**漏传 `size=` 参数** → 回落默认
- `/v1/chat/completions` 经 `_prepare_diffusion_image_request` → `_resolve_height_width_from_extra_body`
  **能正确解析并传递尺寸**

**四条提交核验一致（10-04 / UP74 / origin/main / HEAD）→ 既有缺陷，非本轮合并引入。**

**§6.3 操作指引**：手册列出的「Qwen t2i 2048²/2752×1536」必须走
**`/v1/chat/completions`**；用 `/v1/images/generations` 会一律得到 1024²（与现网行为一致）。
